# Demo — results

Generated by `node scripts/demo.mjs`: 1,500,000 particles, 10 s each, alone in headless Chromium, the first second left out. Machine: Intel(R) Xeon(R) Processor @ 2.10GHz. The same page runs the three versions; only the code of a frame differs ([page](page.js)). A frame is late when it comes more than 4 ms after the 60 Hz it aims at. The memory is the JavaScript heap, plus, for Peras, the module's memory; a headless browser paints at 60 Hz at most.

What it shows and what it does not. The gap between the two TypeScript versions is the garbage collector's: a new object per particle at each frame, as immutable state is often written, collected again and again. The gap between typed arrays and Peras is WebAssembly's, an owned module (`.peras`) with its loops compiled ahead of time; a managed module (`.apeiron`) compiles to JavaScript and runs at TypeScript's speed ([case study](../case-study/RESULTS.md)). A program in TypeScript written as the middle one gets most of the way.

| Version | Frames per second | Frame computed in (median, 95th percentile) | Frames late | Memory held, lowest to highest |
| --- | --: | --: | --: | --: |
| TypeScript, immutable objects | 7.9 | 80.9 ms, 322.7 ms | 100 % | 231.6 to 1125.5 MiB |
| TypeScript, typed arrays by hand | 46.9 | 19.4 ms, 26.6 ms | 39 % | 48.9 to 49.8 MiB |
| Peras, WebAssembly | 57.7 | 13.5 ms, 21.4 ms | 8 % | 49.1 to 49.9 MiB |
