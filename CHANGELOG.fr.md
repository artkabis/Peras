## Non publié

### Langage et compilateur

- **Fusion, premier cas** : `xs.filter((x) => …).length` compte les éléments gardés dans sa boucle, sans indicateurs ni tableau ([décision 0004](docs/fr/decisions/0004-strings-without-allocation.md)). Une seule fonction s’exécute, comme écrit : l’ordre des appels ne peut pas changer. `words` prend 3,1 ms au lieu de 4,5, contre 10,2 pour JavaScript, avec 5 blocs au lieu de 7.
- **Corrigé** : dans `a && b` et `a || b`, un temporaire de `b`, comme celui que crée `s.endsWith("1")`, était libéré après l’instruction, y compris sur le chemin où `b` ne s’exécute pas : le vérificateur de l’IR refusait le module. Il est maintenant libéré dans la branche qui l’a créé.
- **Le texte entre dans le module en une passe** : le chargeur écrit une chaîne avec `TextEncoder.encodeInto` directement dans la mémoire du module, au lieu de l’encoder dans un nouveau tableau puis de la copier : 0,7 ms au lieu de 3 à 3,7 pour un million de caractères dans Chromium. Une première place d’un octet par caractère et d’un huitième suffit à l’anglais et au français ; les autres textes reçoivent plus de place une fois. `words` prend 4,6 ms au lieu de 7,2, contre 10,3 pour JavaScript ; aucune allocation de plus ([décision 0004](docs/fr/decisions/0004-strings-without-allocation.md)).
- **Flottants en texte** : `toString()` sur un `f64` écrit ce qu’écrit `String()` en JavaScript, le moins de chiffres qui se relisent en le même nombre ; sur un `f32`, le moins de chiffres qui se relisent en ce `f32` (`0.1`, pas `0.10000000149011612`). Une nouvelle fonction du runtime, `fmt_float`, le demande à l’hôte : le chargeur appelle `String()` lui-même, le texte est donc celui de JavaScript par construction, comme pour `Math` ; l’interpréteur et les tests ont les mêmes règles en Rust (`perasc_ir::text::number_text`), vérifiées face à Node sur 6 millions de valeurs, égalités entre deux formes les plus courtes comprises. Mesuré dans Node sur un million de flottants : 272 ms contre 159 pour JavaScript, le coût du passage vers l’hôte et d’une chaîne pour chacun ; les entiers, écrits par le runtime lui-même, prennent 46 ms contre 52. Écrire les chiffres en WebAssembly, avec Ryu ou Schubfach, est l’étape suivante si un programme en a besoin plus vite.
- **Chaînes gabarits** : `` `${name}: ${count} items` `` écrit les chaînes, nombres et booléens comme JavaScript, toute expression dans `${…}`, des gabarits imbriqués, les échappements `` \` `` et `\${`, plusieurs lignes. Le lexeur garde la profondeur des accolades de chaque gabarit ouvert ; le compilateur dimensionne un seul buffer pour tout le texte, une allocation par gabarit. Une structure, un tableau ou une option est refusé (`E0239`). Un test de bout en bout les compare aux gabarits de JavaScript sur les deux allocateurs.
- **`--simd on|off`** (`simd` pour Vite), activé par défaut : le SIMD de WebAssembly dans les boucles vectorielles et dans le runtime, où `split` cherche maintenant un séparateur d’un octet seize octets à la fois. Chaque allocateur est compilé des deux façons. Un module qui se sert du SIMD vérifie, avant de se charger, que le moteur l’a (`WebAssembly.validate` sur un module de 43 octets), et lève sinon un message traduit qui nomme `--simd off` ; `--simd off` compile un module sans aucun SIMD, pour Safari avant 16.4. Mesuré avec `scripts/bench-ab.mjs` : `words` −35 %, `grayscale` −28 %, `particles` −20 %, aucune régression, +671 octets gzip.
- **Des vues pour `split`** ([décision 0004](docs/fr/decisions/0004-strings-without-allocation.md)) : là où le tableau que crée `text.split(sep)` est lu aussitôt, par une méthode ou un `for…of`, ses morceaux sont des vues du texte : un bloc d’en-têtes de chaîne de 16 octets dont les octets sont ceux du texte, au lieu d’un bloc par morceau. Une vue est un en-tête de chaîne ordinaire, que toute opération sur les chaînes lit sans changement ; ses copies sont des chaînes ordinaires. Quand les arguments de la méthode ou le corps de la boucle nomment la variable du texte, le tableau est d’abord copié, et un résultat de `filter` qui sort de l’instruction est une copie. Un séparateur d’un octet est découpé par deux boucles simples. `push` n’appelle le runtime que quand le tampon est plein. `words` prend 11,2 ms au lieu de 17, contre 10,3 pour JavaScript.
- **Le texte, mesuré puis accéléré** : sur les 31 ms du noyau `words`, l’entrée dans le module en UTF-8 en prenait 4 ; le reste était de l’allocation. `filter` sur un tableau temporaire, comme `text.split(" ").filter(…)`, garde ses éléments sur place (`arr_keep`) et donne ce tableau comme résultat, au lieu de copier chaque élément gardé. Un petit tampon dont les éléments ne sont pas des tampons, une chaîne courte, tient en un bloc, ses octets après son en-tête, au lieu de deux ; il sort ses octets quand il grandit. `indexOf` cherche le premier octet de l’aiguille avant de comparer le reste : 12 % plus rapide sur un long texte. Le noyau prend 17 ms : 2 fois le temps de JavaScript, contre 3,4.
- **Corrigé** : `for (const w of text.split(" "))`, une boucle sur un tableau temporaire, était refusée par le vérificateur de l’IR : la première instruction du corps libérait le tableau. Il appartient maintenant à la portée de la boucle, libéré après elle ou par un `return` à l’intérieur.
- **`sort()` est un tri par base** : les nombres deviennent des clés non signées dans le même ordre, triées en 3 passes de 11 bits (6 pour les nombres de 64 bits ; un chiffre identique dans toutes les clés est sauté), puis reconverties ; sous 64 nombres, un tri par insertion sur les mêmes clés. L’ordre est celui des tableaux typés de JavaScript : -0 avant +0, tous les NaN à la fin, en NaN canonique. Avant, le tri par tas du runtime comparait les flottants avec `<`, ce qui laissait NaN et -0 où ils tombaient et pouvait différer de l’interpréteur. Un million de `f64` se trient en 31 ms au lieu de 280 : 4,2 fois plus vite que `Float64Array.prototype.sort`. Il utilise une copie de travail du tableau, rendue avant de terminer. Un test de bout en bout le compare au tri de JavaScript sur quatre types, des longueurs autour de 64, des NaN des deux signes, -0 et les extrêmes.
- **Boucles vectorielles** : une boucle comptée dont les tours sont indépendants (corps sans branchement, chaque élément à l’indice `i`, un seul type parmi `i32`, `f32` et `f64`, opérations exactes dans chaque voie, réductions entières `+ ^ | &`) reçoit une copie qui calcule 4 voies à la fois (2 pour `f64`) avec le SIMD de WebAssembly, avant la boucle scalaire, qui exécute toujours le dernier tour. Les résultats sont bit à bit ceux de la boucle scalaire : les tests comparent les deux sur toutes les longueurs de 0 à 19, et échouent quand le code vectoriel est faux. Le noyau de gris passe d’environ 10 à 5 ms, 2,2 fois la vitesse de JavaScript. Un module qui contient une telle boucle demande le SIMD de WebAssembly (Safari 16.4 et suivants).
- **Boucles vectorielles avec branches** : un `if` qui compare des valeurs de voie (`< <= > >= == !=`, avec `&& || !`, imbriqué ou avec `else`) exécute les deux branches dans chaque voie sous un masque ; une affectation ne garde sa nouvelle valeur que là où la branche s’exécute, et une écriture remet les anciens éléments ailleurs. Une locale affectée dans une branche doit l’avoir été plus tôt dans le même tour, sinon la boucle reste scalaire. Le noyau des particules passe de 21 à 17 ms, 1,8 fois la vitesse de JavaScript. Les tests échouent exprès quand un masque est faux.
- **Contrôles d’indice prouvés inutiles** : dans `for (let i = 0; i < borne; i++)` dont le corps ne fait grandir aucun tableau et n’appelle rien, `xs[i]` n’est plus contrôlé quand `borne` est la longueur de `xs`. Un autre tableau est contrôlé une fois avant la boucle, qui s’exécute telle qu’écrite si le contrôle échoue : elle s’arrête au même endroit, après les mêmes effets. Les boucles imbriquées de même borne héritent de la preuve. Le noyau des particules passe de 24 à 21 ms. Lire longueurs et adresses avant la boucle a aussi été mesuré, puis abandonné : c’était plus lent.
- **Un banc d’essai dans le navigateur** (`bench/browser`, `node scripts/bench-browser.mjs`) : huit noyaux en Peras et en JavaScript, vérifiés égaux puis chronométrés dans Chromium, avec le téléchargement et le démarrage. Peras est 1,2 à 1,3 fois plus rapide sur les nombres d’un `PerasArray`, aussi rapide sur l’arithmétique flottante seule, 1,5 à 1,8 fois plus rapide sur les structures, environ 20 fois sur les entiers 64 bits ; plus lent sur le texte (3,4 fois), sur les appels très courts (1,4 fois) et face au tri natif des tableaux typés (2,3 fois). La CI vérifie que les deux côtés concordent.
- **Corrigé** : un tableau `inout` passé comme tableau typé (`Float64Array`…) levait une erreur après l’appel et laissait son tampon vivant. Ses valeurs sont maintenant recopiées avec `set()` ; si la fonction a changé sa longueur, une `RangeError` est levée après la libération de tous les tampons. Les déclarations TypeScript acceptent le tableau typé des mêmes nombres (`number[] | Float64Array | PerasArray<"f64">`). Le premier commentaire du chargeur n’appelle plus tous les allocateurs « debug ».
- **Nombres en texte** : `toString()` sur les entiers et les booléens écrit ce qu’écrit `String()` en JavaScript ; `parseI32()` et `parseI64()` sur les chaînes donnent `Some(n)` seulement pour un signe ou rien, puis des chiffres ASCII, dans l’intervalle du type, et `None` sinon, jamais une valeur tronquée. Quatre nouvelles fonctions du runtime, `fmt_int`, `fmt_bool`, `str_is_int` et `str_parse_int`, la première prenant un `i64` et la dernière en donnant un.
- **Nombres** : `round`, `sin`, `cos`, `tan`, `exp`, `log`, `pow`, `atan2` et `hypot` sur les flottants. Ceux pour lesquels WebAssembly n’a pas d’instruction sont importés du `Math` de JavaScript, seulement par les modules qui s’en servent : ils donnent donc exactement ce que donne JavaScript ; un `f32` passe par `f64`.
- **Tableaux** : `slice`, `concat`, `reverse`, `sort` (nombres, sur place), `includes` et `indexOf` (nombres, booléens et chaînes), colonne par colonne pour les tableaux de structures.
- **Des tableaux sans copie** : `__perasHeap.array(kind, init)` crée un `PerasArray`, un tableau de nombres dans la mémoire du module. Les fonctions exportées le prennent sans copie : prêté, modifié sur place par `inout`, ou donné à `sink`. `view()` donne un tableau typé sur ses éléments, valable jusqu’au prochain appel au module. Sur un million de `f32`, la lecture passe de 5,2 à 1,5 ms et la modification sur place de 11,5 à 0,8 ms. TypeScript voit `number[] | Float32Array | PerasArray<"f32">` : un tableau typé est copié, comme un tableau.
- **Texte** : `indexOf`, `includes`, `startsWith`, `endsWith`, `slice`, `trim`, `toUpperCase`, `toLowerCase`, `repeat`, `replace`, `replaceAll` et `split` sur les chaînes, et `join` sur les tableaux de chaînes. Les indices comptent les octets UTF-8 ; un indice au milieu d’un caractère recule à son début : une tranche est toujours un texte valide. Ce sont des fonctions du runtime, écrites une seule fois en texte WebAssembly pour les deux allocateurs, appelées par une nouvelle opération de l’IR, `buf.runtime` ; l’interpréteur a les mêmes fonctions en Rust, et les tests vérifient que les deux donnent les mêmes résultats.
- **Fonctions fléchées pour les méthodes de tableaux** : `map`, `filter`, `reduce`, `find`, `findIndex`, `some` et `every` prennent `(x) => …`, écrite sur place et compilée comme le corps d’une boucle, sans valeur de fonction à l’exécution ; `some`, `every`, `find` et `findIndex` s’arrêtent au premier élément qui décide. Les paramètres prêtent les éléments, comme `for…of` ; une valeur que la fonction déplace est vue déplacée au tour suivant (`E0204`). Une fonction fléchée ailleurs est refusée pour l’instant (`E0238`). `reduce` garde des nombres et des structures de nombres.
- `min(b)`, `max(b)` et `clamp(lo, hi)` sur tout nombre.
- **Un allocateur de production, TLSF** ([décision 0002](docs/fr/decisions/0002-tlsf-allocator.md)) : chaque allocation et libération en temps borné, classes de taille trouvées avec `i32.clz` et `i32.ctz`, blocs libérés fusionnés aussitôt avec leurs voisins, et fin du tas rendue. `vite build` le lie, le serveur de développement garde l’allocateur de débogage, et `perasc build --allocator tlsf` le choisit. Il est 2,7 fois plus rapide que l’allocateur de débogage sur un programme qui alloue 6 millions de blocs. Les deux allocateurs partagent les fonctions de tampons, écrites une seule fois.
- **Méthodes et interfaces.** `impl Point { fn norm(self): f64 { … } }` donne ses méthodes à une structure ou une énumération du module (`E0234` sinon).
  - `self`, `inout self` ou `sink self` vient en premier ; `p.shift(1.0)` n’a pas besoin de `&`, et `p` doit être un `let`. Une méthode sans `self` s’appelle sur son type, `Point.origin()`, et toute méthode peut s’appeler ainsi, son `self` en premier. `Self` nomme le type ; `impl<T> Stack<T>` donne ses méthodes à un type générique.
  - `interface Shape { fn area(self): f64; }` et `impl Shape for Circle { … }` : une implémentation fournit exactement les méthodes de l’interface (`E0235`), avec exactement leurs signatures (`E0236`).
  - Une interface est une contrainte, `fn total<T: Shape>(…)` : chaque instance de la fonction appelle la méthode de son type, résolue à la compilation, sans table à l’exécution. Utilisée comme type, elle est refusée (`E0237`).
- **Tuples** : `(i32, String)`, écrits `(1, "a")`, lus avec `.0`, `.1`, imbriqués `t.1.0`. Un tuple est une structure générique, gardée comme ses champs ; JavaScript voit un tableau, typé `[number, string]`.
- **Alias de types** : `type Meters = f64;` et `type Grid<T> = Array<Array<T>>;`, interchangeables avec ce qu’ils nomment ; un alias qui se contient est refusé (`E0232`).
- **Les constantes de module se compilent** : `const AREA: i32 = SIDE * SIDE;` est écrite là où elle sert. Sa valeur doit être connue à la compilation (`E0233`). Le `let` de module reste seulement vérifié.
- Une structure qui se contient à travers un tableau, `struct Tree { children: Array<Tree> }`, ne fait plus planter le compilateur par débordement de pile : elle est signalée comme pas encore compilée (`E0900`).
- Les **génériques**, sur les fonctions, les structures et les énumérations : `fn larger<T: Ord>(a: T, b: T): T`, `struct Pair<A, B>`, `enum Tree<T>`.
  - Six contraintes prédéfinies : `Eq`, `Ord`, `Numeric`, `Integer`, `Float` et `Copy`. Un corps générique est vérifié une fois, pour tous les types que ses paramètres peuvent représenter : une opération que ses contraintes ne permettent pas est refusée, avec une correction qui ajoute la contrainte (`E0228`) ; une utilisation avec un type qui n’en respecte pas une est refusée (`E0227`), de même qu’une contrainte inconnue (`E0226`).
  - Les arguments de type sont inférés des arguments et du type attendu, ou écrits à l’appel, `larger<i64>(a, b)` : les comparaisons enchaînées étant refusées, ce n’est jamais une comparaison. Quand rien ne les détermine, `E0229`.
  - Une valeur d’un paramètre de type se déplace, sauf si le paramètre est `Copy` ; `Ord` et `Numeric` l’impliquent.
  - Compilés par monomorphisation : une copie par jeu d’arguments de type utilisé par le module, nommée d’après eux (`larger__i64`), sans coût à l’exécution. Une fonction générique jamais appelée est vérifiée, pas compilée. Une fonction exportée ne peut pas être générique (`E0230`), et le code générique qui demanderait des copies pour des types toujours plus grands est refusé (`E0231`).
  - Les structures et énumérations génériques arrivent en JavaScript comme des interfaces et des unions nommées d’après leurs arguments, `Pair_i32_String`.
- `unwrapOr` avec une valeur de secours lue dans une variable contenant une chaîne ou un tableau ne produit plus de code refusé par le vérificateur : la valeur de secours est copiée.
- Les **structures** se compilent, comme des valeurs : chacune est remplacée par ses champs scalaires, structures imbriquées aplaties, si bien qu’elle ne touche jamais le tas.
  - Un paramètre structure devient un paramètre par champ.
  - Une fonction qui renvoie une structure renvoie un résultat WebAssembly par champ, et un tuple dans le backend Rust.
  - Les champs se lisent et s’écrivent, affectations composées comprises ; une structure se copie par affectation ; `p = Point(p.y, p.x)` échange.
  - Les appels qui renvoient une structure s’exécutent d’abord, dans des temporaires, sans changer l’ordre d’évaluation : à droite de `&&` et `||` seulement quand ils s’exécuteraient, et dans une condition de boucle à chaque tour.
  - Les fonctions exportées prennent et renvoient des objets JavaScript, déclarés comme interfaces TypeScript.
- **`Result<T, E>`** : `Ok(valeur)` ou `Err(erreur)`, `isOk`, `isErr`, `unwrapOr`, et `?`, qui renvoie l’erreur tout de suite ; la fonction doit renvoyer un résultat avec le même type d’erreur, ou une option pour `?` sur une option (`E0225`). L’erreur se déplace dans le retour, buffers compris.
- L’exhaustivité et les bras inatteignables sont maintenant vérifiés par l’algorithme de Maranget, si bien que les motifs imbriqués comptent : `Err(Empty)` et `Err(NotADigit(_))` couvrent ensemble `Err`. Un type du module peut prendre le nom d’un type intégré, comme `Result`.
- **Énumérations avec données, et `match`.** `enum Shape { Circle(f64), Rect(f64, f64), Empty }` ; les valeurs s’écrivent `Shape.Circle(1.0)`.
  - `match` décompose une valeur avec des motifs : `_`, noms, nombres et booléens, variantes avec leurs données, imbriqués ; les bras sont des valeurs ou des blocs, et `return`, `break`, `continue` y marchent.
  - Chaque `match` doit couvrir chaque valeur (`E0222`) ; une variante inconnue (`E0223`) et un bras qu’aucune valeur n’atteint (`E0224`) sont aussi des erreurs. Un `match` dont tous les bras renvoient termine la fonction.
  - Les options se filtrent aussi (`Some(x)`, `None`), et une option ou une énumération peut désormais contenir des chaînes et des tableaux : les données des variantes non prises sont des buffers vides, si bien que la valeur possède toujours les mêmes. `pop()` sur un tableau de chaînes marche désormais.
  - JavaScript voit `{ kind: "Circle", values: [1] }`, déclaré à TypeScript comme une union.
- Les **tableaux de chaînes et de tableaux** se compilent, ainsi que les structures qui en contiennent dans des tableaux : un buffer peut posséder des buffers, que le runtime libère et copie avec lui, à toute profondeur. JavaScript les passe et les reçoit en tableaux et objets imbriqués.
- E0204 raconte l’histoire de la valeur : où elle a reçu sa valeur, où elle a été déplacée, où elle est réutilisée.
- Les **tableaux de structures et d’options** se compilent, en colonnes : un buffer par scalaire d’un élément, si bien que `points[i].x` et une boucle sur un seul champ ne touchent qu’un buffer. L’indexation, `points[i].x = v`, `push`, `pop`, `copy`, `==` et `for…of` marchent colonne par colonne ; JavaScript voit des tableaux d’objets.
- **`inout`** marche sur tous les types : la fonction rend ses nombres en résultats supplémentaires, réécrits dans les variables de l’appelant ; tableaux et chaînes changent sur place. Depuis JavaScript, une structure passée `inout` est un objet dont les champs sont mis à jour. Une variable passée `inout` ne peut pas être lue ailleurs dans la même instruction (`E0207`), et deux champs différents d’une structure ne comptent plus comme des alias.
- `?` libère maintenant les tableaux et les chaînes que la fonction détient avant de renvoyer `None` ; ils fuyaient avant.
- Les **chaînes** se compilent, en UTF-8 : littéraux, `+`, `+=`, `==`, `!=`, `length` en octets et `copy()`. Un littéral est stocké une seule fois, en segment de données passif, et copié dans un nouveau buffer avec `memory.init` ; `+=` ajoute sur place. JavaScript passe et reçoit des chaînes, encodées et décodées en UTF-8. `==` compare aussi les tableaux, élément par élément.
- Les **tableaux** se compilent, de nombres et de booléens, sur le tas : littéraux, `length`, lecture et affectation par indice, `push`, `pop`, `copy`, `for…of`.
  - Chaque indice est vérifié ; un indice hors limites arrête le programme avec une `RangeError`, en anglais ou en français, avant de toucher la mémoire.
  - Un tableau est un en-tête de 12 octets, qui garde son adresse, et ses éléments ; `push` double la place quand elle manque. L’allocateur de débogage tient les deux blocs, si bien que chaque bug mémoire reste détecté.
  - JavaScript passe et reçoit des copies, en `number[]`, `bigint[]` ou `boolean[]` ; un paramètre `inout` est recopié.
- La **possession** est vérifiée : une valeur sur le tas a un seul propriétaire, se déplace à l’affectation, au `return` et vers `sink`, et est empruntée sinon.
  - Quatre nouvelles erreurs : une valeur utilisée après son déplacement ([E0204](docs/fr/errors/E0204.md)), `&` manquant ou en trop sur un argument `inout` ([E0206](docs/fr/errors/E0206.md)), deux arguments qui atteignent une variable que l’un modifie, ou un tableau modifié pendant que `for…of` le parcourt ([E0207](docs/fr/errors/E0207.md)), le déplacement de ce qui n’est qu’emprunté ([E0209](docs/fr/errors/E0209.md)). Chaque correction ajoute `.copy()`, `&` ou `sink` là où c’est possible.
  - Le lowering insère chaque libération : en fin de portée, à la réaffectation, avant `return`, `break` et `continue`, et là où des chemins se rejoignent après un déplacement sur l’un d’eux. Le vérificateur de libérations prouve chacune ; les programmes de test ne laissent aucun bloc vivant, dans l’interpréteur et en WebAssembly sur l’allocateur de débogage.
- Les **options** se compilent, sans le tas elles aussi : une `Option<T>` est un `bool` suivi des scalaires de `T`, n’importe quel `T` compilé, structures comprises.
  - `Some`, `None`, `isSome`, `isNone`, `unwrapOr`, et `?`, qui renvoie `None` tout de suite depuis une fonction qui renvoie une option.
  - `checkedAdd`, `checkedSub` et `checkedMul` sur `i32` et `i64` donnent `None` en cas de dépassement ; ils sont testés contre ceux de Rust sur les valeurs où le dépassement commence et s’arrête.
  - `None` et `[]` prennent le type qu’attend leur contexte.
  - JavaScript voit la valeur ou `undefined`, déclarée `T | undefined`.
- Le chargeur JavaScript préfixe par `$` chaque nom qu’il déclare, ce par quoi un nom Peras ne peut pas commencer : une fonction ou un paramètre nommé `r`, `url` ou `runtime` ne casse plus le module.
- L’IR vérifie la possession : poignées `owned` et `borrowed`, libérations explicites, et un vérificateur qui prouve que chaque bloc est libéré exactement une fois sur chaque chemin. L’allocateur de débogage est intégré aux modules qui utilisent le tas ; un bug mémoire lève une `PerasMemoryError` qui nomme les deux sites, en anglais ou en français. Rien dans le langage n’alloue encore.

### Banc d’essai

- **D’autres moteurs et de vrais appareils** : `scripts/bench-browser.mjs` et `scripts/bench-ab.mjs` prennent `--browser chromium|firefox|webkit`, et `--serve` (avec `--host`, `--port`) pour ouvrir la page à la main dans n’importe quel navigateur, un vrai Safari compris, qui affiche alors lui-même ses résultats. La CI lance les deux bancs dans WebKit, le moteur de Safari, et met les rapports dans le résumé de l’exécution : jusque-là, chaque chiffre est celui de Chromium.
- **Un banc A/B**, `scripts/bench-ab.mjs` : deux compilations (`current`, `ref:<référence git>`, `bin:<chemin>`, chacune avec ses options) comparées sur les noyaux du navigateur dans une même page, 4 tours en alternant celle qui passe en premier, avec un verdict sur des seuils fixés : un gain à 10 % à chaque tour, une régression à 3 % à chaque tour, les allocations, +1 Kio gzip, +10 % de temps de compilation. Une compilation comparée à elle-même reste sous 3 %. La CI le lance avec `--check`. Le programme du banc prépare maintenant ses noyaux pour un nombre quelconque de compilations.
- **La décision 0004, mesurée d’abord** ([décision 0004](docs/fr/decisions/0004-strings-without-allocation.md)) : du texte sans une allocation par morceau. Des fonctions écrites à la main dans un runtime à part fixent le plafond de chaque voie dans Chromium : compter les mots d’un million de caractères sans aucun tableau prend 7,3 à 7,6 ms, avec des vues 7,8 à 8,0 ms, contre 19 à 21 ms aujourd’hui et 10,4 à 10,8 ms pour JavaScript. Les vues viennent d’abord, choisies par le compilateur là où il prouve qu’un morceau ne survit pas à son texte ; la fusion des chaînes de méthodes suit.
- `overflows` exerce les options et l’arithmétique vérifiée ; les deux backends s’accordent avec la référence JavaScript.
- `cmandel` calcule l’ensemble de Mandelbrot avec `struct Complex`. Les deux backends s’accordent avec la référence JavaScript. Le backend direct prend 15 ms contre 13 ms pour le code `f64` simple et pour Rust ; JavaScript, qui alloue un objet par nombre complexe, prend 49 ms. L’optimiseur ne touche pas encore aux fonctions à plusieurs résultats.

## 0.0.1 — 4 novembre 2026

La fin de la phase 0 du [plan de démarrage](docs/fr/kickoff-plan.md) : une fonction `.peras` se compile en WebAssembly et s’exécute dans le navigateur via Vite, et chaque erreur affiche un extrait, une cause et une correction, en anglais et en français.

### Langage et compilateur

- Lexer, parser, vérification des noms et des types pour les fonctions, `let` et `const`, `struct`, les tableaux, `if`, `while`, `for` et `for…of`. Toutes les erreurs sont signalées en une passe, avec un code stable, une cause, une correction sous forme de diff et une page `perasc explain`.
- 46 codes d’erreur, chacun avec sa page en anglais et en français ; on vérifie que l’exemple de chaque page produit son code et que sa correction le fait disparaître.
- `perasc check`, `perasc build` et `perasc explain`, avec `--lang en|fr`, `--json` et `--color`.
- Génération de code pour les fonctions sur des nombres et des booléens :
  - un backend WebAssembly direct, par défaut, qui ne demande aucun autre outil ;
  - un backend Rust, utilisé en CI pour contrôler le premier ([décision 0001](docs/fr/decisions/0001-webassembly-backend.md)).
- Optimisations de l’IR, chacune mesurée face à Rust et vérifiée par un vérificateur d’IR et un test différentiel :
  - élimination de la récursion avec accumulateur ;
  - déroulage de la récursion ;
  - rotation du test de sortie ;
  - `abs` entier sans branchement ;
  - doublement écrit comme une addition ;
  - sortie des invariants de boucle.

  Sur les noyaux du banc d’essai, le backend direct est au niveau du backend Rust.

### Outillage

- `vite-plugin-peras` importe un fichier `.peras` comme un module. Il affiche les erreurs dans l’overlay de Vite, fait échouer `vite build` en cas d’erreur et écrit les déclarations TypeScript à côté de la source.
- `examples/fib` exécute `fib` dans le navigateur.

### Contrôles qualité

Chaque contrôle bloque la fusion :

- formatage ;
- lints sans aucun avertissement ;
- tests unitaires, tests d’interface et tests de bout en bout dans Chromium sans interface ;
- `cargo deny` et `pnpm audit` sans CVE connue ;
- accord des deux backends ;
- traductions complètes ;
- fuzzing nocturne du lexer, du parser et de toute la chaîne.

### Limites connues

- Chaînes, tableaux, structures, méthodes et `Option` sont vérifiés mais pas encore compilés : la génération de code les signale avec `E0900`.
- L’ownership, les modules `.apeiron` et la bibliothèque standard arrivent dans les phases suivantes.
