## Unreleased

### Language and compiler

- **Threads: `parallel for`** ([decision 0007](docs/en/decisions/0007-threads-over-shared-memory.md)): `parallel for (let i = start; i < end; i++)` marks a loop whose turns may run on several threads at once. The compiler proves them independent, each turn writing only the elements at its own index, and refuses one that could see another with its reason (`E0241`); the results are those of the loop run in order, bit for bit. `perasc build --threads on`, or `threads: true` for Vite, runs them on every core of a cross-origin isolated page, over one shared memory with no copy, and on one thread elsewhere; Vite's dev server sends the two headers. On 4 cores, 200 steps of a million particles run 2.7 to 2.8 times faster than on one thread, a grayscale filter 1.7 to 1.9 times. A loop that starts at a local, as a job does, now has its bounds checks proven away too, with `start >= 0` in the guard.
- **`Map` and `Set`, complete** ([decision 0005](docs/en/decisions/0005-maps-and-sets.md)): `for (const entry of m)` walks the entries in insertion order, each lent as `(key, value)`, and `for (const k of s)` the keys of a set; values of any type, strings, arrays, structures, options, other maps, which the map owns and releases; maps held by structures, arrays, options and other maps, copied deeply with them, and `m.copy()`; and exported functions that take and give JavaScript's `Map` and `Set`, copied in insertion order, declared to TypeScript as `ReadonlyMap` for a parameter only read. The runtime keeps a value as its scalars, one 64-bit slot each. Tested against Rust's maps in WebAssembly and in the interpreter and against JavaScript's in Chromium, with no leak.
- **Fixed**: in `m.set(k, v)` and `s.add(k)`, a key whose computation needed a temporary, as `(e.1 % 7).toI64()`, was evaluated before the statements that compute it, and read a stale value.
- **Decision 0007, threads over shared memory** ([decision 0007](docs/en/decisions/0007-threads-over-shared-memory.md)): measured first. `bench-workers` gains a ceiling, each worker's part kept in its memory and only the kernel and the answers timed, checked element by element: on 4 cores, grayscale goes from 0.32–0.35 to 1.84–2.02 times the direct speed, particles from 0.80–0.83 to 2.08–2.22 (10 steps) and from 2.7–3.0 to 3.0–3.3 (200 steps). Peras will build `--threads`: one shared memory, parallel loops split by ownership into disjoint ranges with the rule of vector loops, one allocator arena per thread, a pool kept by the loader; a page not cross-origin isolated runs on one core with the same results.
- **`Map` and `Set`, first part** ([decision 0005](docs/en/decisions/0005-maps-and-sets.md)): `Map<K, V>` and `Set<T>` with integer, boolean and string keys and number or boolean values: `Map.new()`, `set`, `add`, `get`, `has`, `delete`, `clear`, `size`. The table is the runtime's, in insertion order, hashed with SipHash-1-3 under a key the loader draws with `crypto.getRandomValues`, only for a module that has maps. Another key type is refused (`E0240`); values that own buffers, `for…of` over a map and maps across the JavaScript boundary report `E0900` for now. Tested against Rust's `HashMap` in WebAssembly and in the interpreter, and against JavaScript's `Map` and `Set` in Chromium, with no leak.
- **Smaller modules**: a module imports only the runtime functions it calls; its loader embeds the runtime pruned to those and to what the loader calls, every function they reach and nothing else, the names section dropped (`perasc_runtime::prune`, with `wasm-encoder`'s re-encoder, no new dependency); and the loader carries only the helpers its functions use, the public API (`__perasHeap`, `PerasArray`) kept. gzip, loader and module: 13.3 to 8.7 KiB for the browser kernels (−34 %), 11.3–11.5 to 4.5–5.7 KiB for a small module over an array or a text (−49 to −59 %). The standalone loader now compiles the `.wasm` while it downloads, as the Vite plugin's did. No kernel slower; the import time did not move with the bytes.
- **Licence** ([decision 0006](docs/en/decisions/0006-licensing.md)): Peras is under the AGPL-3.0-or-later, with the Peras Runtime Exception, which leaves the programs compiled with Peras to their authors, under the terms they choose. Examples are under 0BSD. The memory leak analyzer and the VS Code extension will be separate, proprietary tools. Contributions grant the project's owner the right to license them under other terms too. The manifests said `MIT OR Apache-2.0` as a placeholder until now.
- **Before using Peras in production**: the roadmap lists what an outside review found and what holds, each as work for a phase.
- **Documentation**: the README gives today's status instead of phase 0's, the speed against JavaScript written for speed, and links to the guide, the reference, the error codes, the five decisions and the benchmarks; the status page lists template literals, and links `Map` and `Set` to decision 0005.
- **Decision 0005, maps and sets** ([decision 0005](docs/en/decisions/0005-maps-and-sets.md)): `Map` and `Set` will keep insertion order, in CPython's compact layout, and hash with SipHash-1-3 under a secret key the loader draws for each instance, which the order keeps out of every result. Measured first, with prototypes in WebAssembly in Chromium: every variant is faster than JavaScript's `Map` (the chosen one 2.2 to 3.2 times on a million integers, 2.4 to 2.6 on counting words); a hash without a key took 18 s instead of 0.18 on identifiers in steps of 4096; Swiss tables are 1.4 to 1.5 times faster but would give back their entries in an order that changes with the key, set aside until the compiler can give them to maps whose order cannot be seen.
- **Fusion, first case**: `xs.filter((x) => …).length` counts the elements kept in its loop, with no flags and no array ([decision 0004](docs/en/decisions/0004-strings-without-allocation.md)). One function runs as written, so the order of calls cannot change. `words` takes 3.1 ms instead of 4.5, against 10.2 for JavaScript, with 5 blocks instead of 7.
- **Fixed**: in `a && b` and `a || b`, a temporary of `b`, as `s.endsWith("1")` makes, was released after the statement, also on the path where `b` does not run: the IR verifier refused the module. It is now released in the branch that made it.
- **Text crosses into the module in one pass**: the loader writes a string with `TextEncoder.encodeInto` straight into the module's memory, instead of encoding it into a new array then copying it: 0.7 ms instead of 3 to 3.7 for a million characters in Chromium. A first room of one byte per character and an eighth fits English and French; other texts get more room once. `words` takes 4.6 ms instead of 7.2, against 10.3 for JavaScript; no more allocations ([decision 0004](docs/en/decisions/0004-strings-without-allocation.md)).
- **Floats as text**: `toString()` on `f64` writes what JavaScript's `String()` writes, the fewest digits that read back as the same number; on `f32`, the fewest that read back as that `f32` (`0.1`, not `0.10000000149011612`). A new function of the runtime, `fmt_float`, asks the host: the loader calls `String()` itself, so the text is JavaScript's by construction, as `Math` functions are; the interpreter and the tests have the same rules in Rust (`perasc_ir::text::number_text`), checked against Node on 6 million values, ties between two shortest forms included. Measured in Node on a million floats: 272 ms against 159 for JavaScript, the cost of crossing to the host and of one string each; integers, written by the runtime itself, take 46 ms against 52. Writing the digits in WebAssembly, with Ryu or Schubfach, is the next step if a program needs it faster.
- **Template literals**: `` `${name}: ${count} items` `` writes strings, numbers and booleans as JavaScript does, any expression inside `${…}`, nested templates, `` \` `` and `\${` escapes, several lines. The lexer keeps the depth of braces of each open template; the compiler sizes one buffer for the whole text, one allocation per template. A structure, an array or an option is refused (`E0239`). An end-to-end test compares them with JavaScript's template literals on both allocators.
- **`--simd on|off`** (`simd` for Vite), on by default: WebAssembly SIMD in vector loops and in the runtime, where `split` now looks for a one-byte separator sixteen bytes at a time. Each allocator is built both ways. A module that uses SIMD checks, before loading, that the engine has it (`WebAssembly.validate` on a 43-byte module) and throws a translated message that names `--simd off` otherwise; `--simd off` builds a module with no SIMD at all, for Safari before 16.4. Measured with `scripts/bench-ab.mjs`: `words` −35 %, `grayscale` −28 %, `particles` −20 %, no regression, +671 bytes gzip.
- **Views of `split`** ([decision 0004](docs/en/decisions/0004-strings-without-allocation.md)): where the array `text.split(sep)` makes is read at once, by a method or a `for…of`, its parts are views of the text: one block of 16-byte string headers whose bytes are the text's, instead of a block per part. A view is an ordinary string header, so every string operation reads it unchanged; copies of it are ordinary strings. When the method's arguments or the loop's body name the text's variable, the array is copied first, and a `filter` result leaving the statement is a copy. A one-byte separator is split by two plain loops. `push` calls the runtime only when the buffer is full. `words` takes 11.2 ms instead of 17, against 10.3 for JavaScript.
- **Text, measured then made faster**: of the 31 ms the `words` kernel took, crossing into the module in UTF-8 was 4; the rest was allocation. `filter` on a temporary array, as `text.split(" ").filter(…)`, keeps its elements in place (`arr_keep`) and gives that array as its result, instead of copying every element kept. A small buffer whose elements are not buffers, a short string, is one block, its bytes after its header, instead of two; it moves its bytes out when it grows. `indexOf` looks for the first byte of the needle before comparing the rest: 12 % faster on a long text. The kernel takes 17 ms: 2 times JavaScript's, where it was 3.4.
- **Fixed**: `for (const w of text.split(" "))`, a loop over a temporary array, was refused by the IR verifier: the first statement of the body released the array. It now belongs to the loop's scope, released after the loop or by a `return` inside it.
- **`sort()` is a radix sort**: numbers become unsigned keys in the same order, sorted in 3 passes of 11 bits (6 for 64-bit numbers; a digit the same in every key is skipped), then turned back; below 64 numbers, an insertion sort on the same keys. The order is that of JavaScript's typed arrays: -0 before +0, every NaN last, as the canonical NaN. Before, the runtime's heapsort compared floats with `<`, which left NaN and -0 where they fell and could disagree with the interpreter. One million `f64` sort in 31 ms instead of 280: 4.2 times faster than `Float64Array.prototype.sort`. It uses a scratch copy of the array, released before it returns. An end-to-end test compares it with JavaScript's sort on four types, lengths around 64, NaN of both signs, -0 and the extremes.
- **Vector loops**: a counted loop whose turns are independent (straight-line body, every element at index `i`, one type among `i32`, `f32` and `f64`, operations exact in every lane, integer reductions `+ ^ | &`) gets a copy running 4 lanes at once (2 for `f64`) with WebAssembly SIMD, before the scalar loop, which always runs the last turn. Results are bit for bit those of the scalar loop: tests compare both on every length from 0 to 19, and break on purpose when the vector code is wrong. The grayscale kernel goes from about 10 to 5 ms, 2.2 times JavaScript's speed. A module with such a loop needs WebAssembly SIMD (Safari 16.4 and later).
- **Vector loops with branches**: an `if` comparing lane values (`< <= > >= == !=`, with `&& || !`, nested or with `else`) runs both branches in every lane under a mask; assignments keep their new value only where the branch runs, and stores write the old elements back elsewhere. A local assigned in a branch must be assigned earlier in the same turn, or the loop stays scalar. The particles kernel goes from 21 to 17 ms, 1.8 times JavaScript's speed. Tests break on purpose when a mask is wrong.
- **Bounds checks proven away**: in `for (let i = 0; i < bound; i++)` whose body grows no array and calls nothing, `xs[i]` is no longer checked when `bound` is the length of `xs`. Another array is checked once before the loop, which runs as written when the check fails, so it traps at the same place after the same effects. Nested loops with the same bound inherit the proof. The particles kernel goes from 24 to 21 ms. Reading lengths and addresses before the loop was measured too, and dropped: it was slower.
- **A browser benchmark** (`bench/browser`, `node scripts/bench-browser.mjs`): eight kernels in Peras and in JavaScript, checked equal then timed in Chromium, with download and start time. Peras is 1.2 to 1.3 times faster on numbers in a `PerasArray`, as fast on floating-point arithmetic alone, 1.5 to 1.8 times faster on structures, about 20 times on 64-bit integers; slower on text (3.4 times), on very short calls (1.4 times) and against the native sort of typed arrays (2.3 times). CI checks that both sides agree.
- **Fixed**: an `inout` array passed as a typed array (`Float64Array`…) threw after the call and left its buffer alive. Its values are now copied back with `set()`; when the function changed its length, a `RangeError` is thrown after every buffer is released. The TypeScript declarations accept the typed array of the same numbers (`number[] | Float64Array | PerasArray<"f64">`). The loader's first comment no longer calls every allocator the debug one.
- **Numbers as text**: `toString()` on integers and booleans writes what JavaScript's `String()` writes; `parseI32()` and `parseI64()` on strings give `Some(n)` only for a sign or none, then ASCII digits, in the type's range, and `None` otherwise, never a wrapped value. Four new functions of the runtime, `fmt_int`, `fmt_bool`, `str_is_int` and `str_parse_int`, the first taking an `i64` and the last giving one.
- **Numbers**: `round`, `sin`, `cos`, `tan`, `exp`, `log`, `pow`, `atan2` and `hypot` on floats. Those WebAssembly has no instruction for are imported from JavaScript's `Math`, only by the modules that use them, so they give exactly what JavaScript gives; an `f32` goes through `f64`.
- **Arrays**: `slice`, `concat`, `reverse`, `sort` (numbers, in place), `includes` and `indexOf` (numbers, booleans and strings), column by column for arrays of structures.
- **Arrays without a copy**: `__perasHeap.array(kind, init)` makes a `PerasArray`, an array of numbers in the module's memory. Exported functions take it with no copy: lent, changed in place by `inout`, or given to `sink`. `view()` gives a typed array over its elements, valid until the next call into the module. On a million `f32`, reading goes from 5.2 to 1.5 ms and changing in place from 11.5 to 0.8 ms. TypeScript sees `number[] | Float32Array | PerasArray<"f32">`: a typed array is copied, as an array is.
- **Text**: `indexOf`, `includes`, `startsWith`, `endsWith`, `slice`, `trim`, `toUpperCase`, `toLowerCase`, `repeat`, `replace`, `replaceAll` and `split` on strings, and `join` on arrays of strings. Indices count bytes of UTF-8; one inside a character moves back to its start, so a slice is always valid text. They are functions of the runtime, written once in WebAssembly text for both allocators, called through a new IR operation, `buf.runtime`; the interpreter has the same functions in Rust, and the tests check that both give the same results.
- **Arrow functions for array methods**: `map`, `filter`, `reduce`, `find`, `findIndex`, `some` and `every` take `(x) => …`, written in place and compiled as the body of a loop, with no function value at run time; `some`, `every`, `find` and `findIndex` stop at the first element that decides. Parameters lend the elements, as `for…of` does; a value the function moves is seen moved at the next turn (`E0204`). An arrow function anywhere else is refused for now (`E0238`). `reduce` keeps numbers and structures of them.
- `min(b)`, `max(b)` and `clamp(lo, hi)` on every number.
- **A production allocator, TLSF** ([decision 0002](docs/en/decisions/0002-tlsf-allocator.md)): every allocation and release in bounded time, size classes found with `i32.clz` and `i32.ctz`, freed blocks merged at once with their neighbours, and the end of the heap given back. `vite build` links it, the dev server keeps the debug allocator, and `perasc build --allocator tlsf` chooses it. It is 2.7 times faster than the debug allocator on a program that allocates 6 million blocks. Both allocators share the buffer functions, written once.
- **Methods and interfaces.** `impl Point { fn norm(self): f64 { … } }` gives a structure or an enumeration of the module its methods (`E0234` otherwise).
  - `self`, `inout self` or `sink self` comes first; `p.shift(1.0)` needs no `&`, and `p` must be a `let`. A method without `self` is called on its type, `Point.origin()`, and any method can be called that way with its `self` first. `Self` names the type; `impl<T> Stack<T>` gives a generic type its methods.
  - `interface Shape { fn area(self): f64; }` and `impl Shape for Circle { … }`: an implementation provides exactly the interface's methods (`E0235`), with exactly their signatures (`E0236`).
  - An interface is a constraint, `fn total<T: Shape>(…)`: each instance of the function calls the method of its type, resolved when compiling, with no table at run time. Used as a type, it is refused (`E0237`).
- **Tuples**: `(i32, String)`, written `(1, "a")`, read with `.0`, `.1`, nested `t.1.0`. A tuple is a generic structure, kept as its fields; JavaScript sees an array, typed `[number, string]`.
- **Type aliases**: `type Meters = f64;` and `type Grid<T> = Array<Array<T>>;`, interchangeable with what they name; one that contains itself is refused (`E0232`).
- **Module constants compile**: `const AREA: i32 = SIDE * SIDE;` is written where it is used. Its value must be known when compiling (`E0233`). Module `let` stays checked only.
- A structure that contains itself through an array, `struct Tree { children: Array<Tree> }`, no longer crashes the compiler with a stack overflow: it is reported as not compiled yet (`E0900`).
- **Generics**, on functions, structures and enumerations: `fn larger<T: Ord>(a: T, b: T): T`, `struct Pair<A, B>`, `enum Tree<T>`.
  - Six built-in constraints: `Eq`, `Ord`, `Numeric`, `Integer`, `Float` and `Copy`. A generic body is checked once, for every type its parameters may stand for: an operation its constraints do not allow is refused, with a fix that adds the constraint (`E0228`); a use with a type that does not meet one is refused (`E0227`), as is an unknown constraint (`E0226`).
  - Type arguments are inferred from the arguments and from the type expected, or written at the call, `larger<i64>(a, b)`: since chained comparisons are refused, this is never a comparison. When nothing determines them, `E0229`.
  - A value of a type parameter moves, unless the parameter is `Copy`; `Ord` and `Numeric` imply it.
  - Compiled by monomorphization: one copy per set of type arguments the module uses, named after them (`larger__i64`), with no cost at run time. A generic function never called is checked, not compiled. Exported functions cannot be generic (`E0230`), and generic code that would need copies for ever larger types is refused (`E0231`).
  - Generic structures and enumerations reach JavaScript as interfaces and unions named after their arguments, `Pair_i32_String`.
- `unwrapOr` with a fallback read from a variable holding a string or an array no longer produces code the verifier rejects: the fallback is copied.
- **Structures** compile, as values: each one is replaced by its scalar fields, nested structures flattened, so it never touches the heap.
  - A structure parameter becomes one parameter per field.
  - A function returning a structure returns one WebAssembly result per field, and a tuple in the Rust backend.
  - Fields are read and written, compound assignments included; a structure is copied by assignment; `p = Point(p.y, p.x)` swaps.
  - Calls returning a structure run first, into temporaries, without changing the order of evaluation: on the right of `&&` and `||` only when it would run, and in a loop condition at every turn.
  - Exported functions take and return JavaScript objects, declared as TypeScript interfaces.
- **`Result<T, E>`**: `Ok(value)` or `Err(error)`, `isOk`, `isErr`, `unwrapOr`, and `?`, which returns the error early; the function must return a result with the same type of error, or an option for `?` on an option (`E0225`). The error moves into the return, buffers included.
- Exhaustiveness and unreachable arms are now checked by the algorithm of Maranget, so nested patterns count: `Err(Empty)` and `Err(NotADigit(_))` together cover `Err`. A type of the module may take the name of a built-in one, such as `Result`.
- **Enumerations with data, and `match`.** `enum Shape { Circle(f64), Rect(f64, f64), Empty }`; values are written `Shape.Circle(1.0)`.
  - `match` takes a value apart with patterns: `_`, names, numbers and booleans, variants with their data, nested; arms are values or blocks, and `return`, `break`, `continue` work inside.
  - Every `match` must cover every value (`E0222`); an unknown variant (`E0223`) and an arm no value can reach (`E0224`) are errors too. A `match` whose arms all return ends the function.
  - Options match too (`Some(x)`, `None`), and an option or an enumeration can now hold strings and arrays: the data of the variants not taken are empty buffers, so the value always owns the same ones. `pop()` on an array of strings now works.
  - JavaScript sees `{ kind: "Circle", values: [1] }`, declared to TypeScript as a union.
- **Arrays of strings and of arrays** compile, and structures holding them in arrays: a buffer can own buffers, which the runtime releases and copies with it, at any depth. JavaScript passes and receives them as nested arrays and objects.
- E0204 tells the value's history: where it received its value, where it moved, where it is used again.
- **Arrays of structures and options** compile, as columns: one buffer per scalar of an element, so `points[i].x` and a loop over one field touch one buffer. Indexing, `points[i].x = v`, `push`, `pop`, `copy`, `==` and `for…of` work column by column; JavaScript sees arrays of objects.
- **`inout`** works on every type: the function gives its numbers back as extra results, written back into the caller's variables; arrays and strings change in place. From JavaScript, a structure passed `inout` is an object whose fields are updated. A variable passed `inout` cannot be read elsewhere in the same statement (`E0207`), and different fields of one structure no longer count as aliases.
- `?` now releases the arrays and strings a function holds before it returns `None`; they leaked before.
- **Strings** compile, in UTF-8: literals, `+`, `+=`, `==`, `!=`, `length` in bytes and `copy()`. A literal is stored once, as a passive data segment, and copied into a new buffer with `memory.init`; `+=` appends in place. JavaScript passes and receives strings, encoded and decoded as UTF-8. `==` also compares arrays, element by element.
- **Arrays** compile, of numbers and booleans, on the heap: literals, `length`, indexing and assignment through an index, `push`, `pop`, `copy`, `for…of`.
  - Every index is checked; one out of bounds stops the program with a `RangeError`, in English or French, before memory is touched.
  - An array is a 12-byte header, which keeps its address, and its elements; `push` doubles the room when it runs out. The debug allocator holds both blocks, so every memory bug stays caught.
  - JavaScript passes and receives copies, as `number[]`, `bigint[]` or `boolean[]`; an `inout` parameter is copied back.
- **Ownership** is checked: a value on the heap has one owner, moves on assignment, `return` and `sink`, and is borrowed otherwise.
  - Four new errors: a value used after it moved ([E0204](docs/en/errors/E0204.md)), `&` missing or extra on an `inout` argument ([E0206](docs/en/errors/E0206.md)), two arguments reaching one variable that one of them changes, or an array changed while `for…of` goes through it ([E0207](docs/en/errors/E0207.md)), moving what is only borrowed ([E0209](docs/en/errors/E0209.md)). Each fix adds `.copy()`, `&` or `sink` where it applies.
  - Lowering inserts every release: at the end of a scope, on reassignment, before `return`, `break` and `continue`, and where paths meet after a move on one of them. The release verifier proves each one; the test programs leave no block alive, in the interpreter and as WebAssembly on the debug allocator.
- **Options** compile, also without the heap: an `Option<T>` is a `bool` followed by the scalars of `T`, any compiled `T`, structures included.
  - `Some`, `None`, `isSome`, `isNone`, `unwrapOr`, and `?`, which returns `None` early from a function returning an option.
  - `checkedAdd`, `checkedSub` and `checkedMul` on `i32` and `i64` give `None` on overflow; they are tested against Rust's own on the values where overflow starts and stops.
  - `None` and `[]` take the type their context expects.
  - JavaScript sees the value or `undefined`, declared as `T | undefined`.
- The JavaScript loader prefixes every name it declares with `$`, which a Peras name cannot start with: a function or a parameter named `r`, `url` or `runtime` no longer breaks the module.
- The IR verifies ownership: `owned` and `borrowed` handles, explicit releases, and a verifier proving that every block is released exactly once on every path. The debug allocator is linked into modules that use the heap; a memory bug throws a `PerasMemoryError` naming both sites, in English or French. Nothing in the language allocates yet.

### Benchmark

- **Vectorizing across the outer loop, a ceiling** (`bench/prototypes/outer-simd`, committed with its command): n-body and Mandelbrot written by hand in Rust, one value and two `f64` lanes at a time, the results the same bit for bit. n-body runs 1.81 to 1.85 times faster than Peras today, as fast over the expert's JavaScript; Mandelbrot 3 to 7 % slower, against an estimate of 1.5 to 1.8 times faster: two neighbouring points rarely escape at the same step. Worth building for inner loops with the same turns in every lane, not for those that end on a condition.
- **Web Workers**: `scripts/bench-workers.mjs` splits kernels of the browser benchmark across 1, 2 and 4 workers, each with its own instance of the module, everything counted from cutting the data to gathering it, and checks every split result equal to the direct one; CI runs the check. On 4 cores: 2.6 to 2.9 times faster where the work outweighs moving the data (a million particles, 200 steps), slower where it does not (one filter pass over 16 MB: 0.17 to 0.19). What is missing is memory shared between workers, not workers.
- **Against Rust and AssemblyScript**: `scripts/bench-browser.mjs --contenders` builds the browser kernels in Rust (wasm-bindgen, release, LTO, SIMD) and in AssemblyScript (`-O3`), written as each language is usually written, their arrays in their module's memory, and checks they give exactly what Peras and JavaScript give; CI runs the check. Over three runs in Chromium, Rust takes 0.94 to 1.05 times Peras's time on n-body, hashing, Mandelbrot and calls, and 1.3 to 1.5 times on particles, grayscale, sort and words; AssemblyScript 2.4 to 7.3 times on arrays, structures and text, the same on arithmetic alone. Idiomatic, not expert, code on both sides: the README says what that leaves open. AssemblyScript 0.28.20 joins the dev dependencies.
- **Against the fastest JavaScript too.** An outside reader asked whether the figures would hold against JavaScript written for speed; some did not. `bench/browser/reference.js` now has an expert twin where an expert writes it otherwise: a loop over the characters for `words`, two 32-bit halves for `hash64`, columns of `Float64Array` for `nbody`, a radix sort for `sort`, each giving the same result (the sort checked element by element). The report gives two ratios, against the usual JavaScript and against the fastest. Against the fastest, over three runs: 64-bit hashing 5.4 times faster (20 against `BigInt`), sorting 1.8 to 1.9 (3.8 to 4.2 against `Float64Array.prototype.sort`), text 1.6 to 1.7 (3.2 to 3.3 against `split`), and structures **the same speed** (0.97 to 1.01; 1.5 times against an object per body). The ratios given against JavaScript in this changelog before this entry are against the usual JavaScript. The bench README now lists what an independent review would still ask, and ideas that go against what was done, to measure.
- **Other engines and real devices**: `scripts/bench-browser.mjs` and `scripts/bench-ab.mjs` take `--browser chromium|firefox|webkit`, and `--serve` (with `--host`, `--port`) to open the page by hand in any browser, a real Safari included, which then shows its results itself. CI runs both benchmarks in WebKit, Safari's engine, and puts the reports in the run's summary: until then, every figure is Chromium's.
- **An A/B benchmark**, `scripts/bench-ab.mjs`: two builds (`current`, `ref:<git ref>`, `bin:<path>`, each with its options) compared on the browser kernels in one page, 4 rounds alternating which runs first, with a verdict on fixed thresholds: a gain at 10 % in every round, a regression at 3 % in every round, allocations, +1 KiB gzip, +10 % compile time. A build compared with itself stays within 3 %. CI runs it with `--check`. The browser runner now prepares its kernels for any number of builds.
- **Decision 0004, measured first** ([decision 0004](docs/en/decisions/0004-strings-without-allocation.md)): text without an allocation per piece. Functions written by hand in a scratch runtime set the ceiling of each path in Chromium: counting the words of a million characters with no array at all takes 7.3 to 7.6 ms, with views 7.8 to 8.0 ms, against 19 to 21 ms today and 10.4 to 10.8 ms for JavaScript. Views come first, chosen by the compiler where it proves a piece does not outlive its text; fusion of chains of methods follows.
- `overflows` exercises options and checked arithmetic; both backends agree with the JavaScript reference.
- `cmandel` computes the Mandelbrot set with `struct Complex`. Both backends agree with the JavaScript reference. The direct backend takes 15 ms against 13 ms for plain `f64` code and for Rust; JavaScript, which allocates an object per complex number, takes 49 ms. The optimizer does not touch functions with several results yet.

## 0.0.1 — 2026-11-04

The end of phase 0 of the [kickoff plan](docs/en/kickoff-plan.md): a `.peras` function compiles to WebAssembly and runs in the browser through Vite, and every error shows an excerpt, a cause and a fix, in English and French.

### Language and compiler

- Lexer, parser, name and type checks for functions, `let` and `const`, `struct`, arrays, `if`, `while`, `for` and `for…of`. Every error is reported in one pass, with a stable code, a cause, a fix as a diff, and a `perasc explain` page.
- 46 error codes, each with its page in English and French; the example of every page is checked to produce its code and its fix to remove it.
- `perasc check`, `perasc build` and `perasc explain`, with `--lang en|fr`, `--json` and `--color`.
- Code generation for functions on numbers and booleans:
  - a direct WebAssembly backend, the default, which needs no other tool;
  - a Rust backend, used in CI as a check of the direct one ([decision 0001](docs/en/decisions/0001-webassembly-backend.md)).
- IR optimizations, each measured against Rust and checked by an IR verifier and a differential test:
  - accumulator recursion elimination;
  - recursion unrolling;
  - exit test rotation;
  - branchless integer `abs`;
  - doubling as an addition;
  - loop-invariant code motion.

  On the benchmark kernels, the direct backend is level with the Rust backend.

### Tooling

- `vite-plugin-peras` imports a `.peras` file as a module. It shows errors in Vite's overlay, fails `vite build` on an error, and writes TypeScript declarations next to the source.
- `examples/fib` runs `fib` in the browser.

### Quality gates

Every check blocks the merge:

- formatting;
- lints with no warning;
- unit tests, UI tests and end-to-end tests in headless Chromium;
- `cargo deny` and `pnpm audit` with no known CVE;
- the two backends agreeing;
- translations complete;
- nightly fuzzing of the lexer, the parser and the whole pipeline.

### Known limits

- Strings, arrays, structures, methods and `Option` are checked but not compiled yet: code generation reports them with `E0900`.
- Ownership, `.apeiron` modules and the standard library come in the next phases.
