# 0014: Data at scale, aggregated in the browser

_French translation: [../../fr/decisions/0014-data-at-scale.md](../../fr/decisions/0014-data-at-scale.md)._

_Status: protocol registered on 2026-11-11 (commit `96e6c43`), amended the same day before any measure: DuckDB-wasm removed (see [Amendment](#amendment-before-any-measure)). Run 1, at commit `b06da25`: five hypotheses refuted, two hold. Results and record below._

_Protocol status: registered before any measure. The results will be added below it, whether they confirm the hypotheses or not; the protocol itself will not change after the first measure, and any departure from it will be listed as such._

## Context

The garden of Apeiron (decision 0013) showed that a program can be smaller than its image; it did not show that Peras helps a company. Its owner said what that means: take in a lot of data and turn it into something on the web page, without friction. That is a different claim, about ingesting, not generating, and it has a strong competitor: TypeScript, which every web team already writes, plainly or optimized by hand.

This study asks, before writing a line of it, whether Peras does the work of a business dashboard faster, in less memory and with less friction than TypeScript does, at sizes from a hundred thousand to four million rows. It is registered so that its answer cannot be bent toward a demo: the data, the query, the versions, the measures and the thresholds are fixed here.

The risks are the ones decision 0013 named, and one more:

- **A demo chosen to win.** The thresholds are set here; a hypothesis refuted is reported as refuted, in the README too.
- **Versions that do not do the same work.** Every version must give the same summary, byte for byte, checked by a hash.
- **A straw man.** The idiomatic TypeScript is what a web developer writes without optimizing; a hand-optimized TypeScript is measured beside it, so that Peras is not judged against the weakest only.
- **Clean data.** Real exports carry broken rows; one row in a thousand is broken here, and every version must count and skip the same ones.

## The data

Rows of sales events, as a CSV export, generated by `scripts/bench-data.mjs` from a fixed seed with the integer hash of decision 0013 (`lowbias32`). The same seed gives the same file; its SHA-256 is recorded with the results.

- **Sizes**: _N_ = 100,000, 1,000,000 and 4,000,000 rows, about 3.5 MB, 35 MB and 140 MB.
- **Header**, then one row per line, ended by `\n`: `ts,user,country,product,amount,qty`.
- **`ts`**: Unix seconds in 2026, from 1,767,225,600 to 1,798,761,599, uniform.
- **`user`**: 1 to 200,000, skewed so that some customers buy often: `1 + floor(u² × 200,000)`, _u_ uniform in [0, 1).
- **`country`**: one of 20 ISO 3166 codes, two capital letters, the first more frequent: index `floor(u^1.5 × 20)`.
- **`product`**: 1 to 5,000, a few best sellers: `1 + floor(u³ × 5,000)`. Its category is `product % 12`, derived, not a column.
- **`amount`**: the unit price in cents, 100 to 99,999.
- **`qty`**: 0 to 5; 0, a cancelled order, in about 2 % of rows.
- **Broken rows**: about one in a thousand, of three kinds in turn: a field missing; an amount that is not an integer (`12a`); an empty line.

A row is **well formed** when it has exactly six fields; `ts`, `user`, `product`, `amount` and `qty` are strict integers (an optional sign, then ASCII digits, nothing else, in the range of a 32-bit signed integer); and `country` is two letters `A` to `Z`. Every other non-empty line after the header is **broken**. A row is **kept** when it is well formed, its `qty` is above 0, and its `ts` is in the second half of 2026, from 1,782,864,000 (1 July) to 1,798,761,600 (1 January 2027) excluded. Its **revenue** is `amount × qty`, in cents, an exact integer.

## The query

What a sales dashboard shows, computed from the bytes of the file:

1. **Counts**: the lines read, the broken rows, the kept rows.
2. **By country and category**: for each pair present among the kept rows, their number and their revenue.
3. **Customers**: for each country, the number of distinct users among its kept rows.
4. **Each day**: the revenue of each of the 184 days from 1 July to 31 December, by `floor((ts − 1,782,864,000) / 86,400)`.
5. **Best sellers**: the 10 products of highest revenue, ties broken by the smaller product number.

The **summary** is these five, written as JSON in a canonical form: keys in the order above, pairs sorted by country then category, countries sorted, integers in decimal. Its SHA-256 must be the same for every version and every size.

Then the page **draws a chart** from the summary: the revenue of each day as a line, the revenue of each country as bars, on a canvas of 1200 × 600 pixels. The chart is drawn by one JavaScript function, shared by every version: what is compared is how the summary is reached, not how it is painted.

## The versions

- **A. TypeScript, idiomatic**: the text from `response.text()`, `split("\n")`, `split(",")`, numbers checked by a regular expression and read by `Number`, `Map` and `Set` keyed by strings, `Array.prototype.sort`. Written as a web developer writes it without optimizing.
- **B. TypeScript, optimized**: the bytes of the `Uint8Array`, read without making strings; integers parsed by hand; keys packed into integers; counts in typed arrays; distinct users in a bitmap.
- **C. Peras**: an owned module compiled to WebAssembly, written as plainly as A in what the language offers: `split`, `parseI32`, `Map`, `Set`, `sortByDescending`. It receives the text or its bytes, whichever the language passes with less copying, and that choice is recorded.
- **D. Peras, in parallel**: C, its rows split into as many chunks as threads at line boundaries, each aggregated in a `parallel for` (decision 0007), then merged; built with `--threads`, measured in a cross-origin isolated page. If `parallel for` cannot express it, D is reported as not expressible, and that is a finding.

Each version is written from the specification above by the Peras authors; that is a threat to validity, listed below.

## Hypotheses

Each with what refutes it. "Speed" is the inverse of the median time to the summary, warm; "at least _k_ times as fast" compares speeds.

- **H1, plain Peras beats plain TypeScript.** C is at least 2 times as fast as A at 1,000,000 and at 4,000,000 rows. _Refuted_ if either ratio is below 2.
- **H2, plain Peras comes close to optimized TypeScript.** C is at least 0.8 times as fast as B at 1,000,000 and at 4,000,000 rows. _Refuted_ if either ratio is below 0.8. This tests the claim of no friction: speed without writing the optimized version.
- **H3, less memory.** C's peak resident memory is at most half of A's at 4,000,000 rows. _Refuted_ above half.
- **H4, a small program.** C ships at most 3 times A's bytes. _Refuted_ above.
- **H5, the cores help.** D is at least 2 times as fast as C at 4,000,000 rows, on the 4 cores of the machine. _Refuted_ below 2, or if D cannot be written.
- **H6, linear.** C's time at 4,000,000 rows is at most 4.4 times its time at 1,000,000. _Refuted_ above.
- **H7, no more code.** C counts at most 1.25 times A's lines. _Refuted_ above.

The time to the first chart, cold, is measured and reported for every version, and tested against no hypothesis.

## Measures

- **Same summary**: SHA-256 of each version's canonical summary, at each size, all equal. A version that differs is excluded from the hypotheses that involve it, and that is reported.
- **Time to the summary, warm**: from the file's bytes in memory, a `Uint8Array`, to the summary as a JavaScript object, including any decoding and any copy into a module; median of 15 runs after 2 of warm-up, the versions alternating, in Chromium, at each size.
- **Time to the first chart, cold**: a new browser context, nothing cached, the program and the data served from a local server; from the start of navigation to the chart painted, the frame after it is drawn; median of 7 loads, at each size.
- **Memory**: the peak resident memory of the page's renderer process, `VmHWM` in Linux's `/proc/<pid>/status`, a new process for each run, minus the same process's peak with the version loaded and the data in memory before the query runs; median of 5 runs, at each size. It counts everything the page holds: the JavaScript heap, the WebAssembly memories, the buffers.
- **Bytes shipped**: the JavaScript and WebAssembly each version loads, minified by Vite where it applies, then gzip.
- **Energy**: the processor's, read from RAPL where the machine gives it; reported as not measured elsewhere, never estimated (decision 0012).
- **Code**: lines without comments or blank lines, of the code that computes the summary from the bytes; the shared chart and page are not counted.

## Threats to validity

- The data is generated; real exports have other distributions, other widths, quoted fields. The CSV here has no quotes, which makes every parser's work simpler than a real export's.
- The authors wrote every version; an expert of one language may write it faster.
- Analytical engines compiled to WebAssembly, such as DuckDB-wasm, are not measured: the project takes no dependency outside Rust, not even in a benchmark (see the amendment). Any comparison with them will cite their published figures, with their source and conditions, and will not be presented as a measure of this study.
- One machine, headless, 4 cores; a phone may order the versions differently. The local server hides the network: the cold times will also be measured under a throttled network as an exploratory figure.
- `VmHWM` counts what a process touched, not what it needed; a version that returns memory sooner is not rewarded for it.

## Consequences

- `bench/data`, `node scripts/bench-data.mjs`, and its results under this protocol; a check in CI that the versions give the same summary at 100,000 rows.
- If the hypotheses hold, the README gains a third demo: a sales dashboard of millions of rows, built in the browser, with its measured figures. If they do not, the results say so, the README too, and the refuted ones name what the compiler must improve, ordered as decision 0011 orders its steps: by measure.

## Amendment, before any measure

On 2026-11-11, after the registration (commit `96e6c43`) and before any version was written or any measure taken, the owner set a principle: Peras takes no dependency on another language than Rust, and a benchmark must not bring one into the repository either. Measuring DuckDB-wasm would have added a package of about 149 MB, at a development version, to what `pnpm audit` watches. The protocol was amended accordingly:

- Version **E, DuckDB-wasm**, is removed.
- The hypotheses that compared Peras with it are removed: registered **H4** (the first chart before the database, cold) and **H5** (as fast as the database, warm), and the first bound of registered **H6** (a hundredth of its bytes); the second bound of H6 is kept, as **H4**.
- The other hypotheses are unchanged and renumbered: registered H7, H8 and H9 are now **H5**, **H6** and **H7**. No threshold changed.
- The cold time to the first chart is kept as a measure, without a hypothesis.

Because no measure had been taken, the amendment cannot have been guided by a result.

## Record of the study

### Decided after the registration, before the first measure

Written with the versions and the script, in commit `b06da25`, before run 1 started:

- **An empty line is a broken row.** The protocol says both "every other non-empty line after the header is broken" and lists "an empty line" among the broken rows; the list is followed. The `\n` that ends the last line starts no line.
- **What C receives.** Peras's `split` and `parseI32` work on a `String`; an array of bytes cannot be read as text. C receives the text: the time of C includes decoding the bytes and the copy of the text into the module.
- **D cannot be written.** `perasc` refuses `bench/data/dashboard-parallel.peras`: `error[E0241]: this loop cannot run in parallel: it makes, grows, moves or releases a string, an array or a map`. The file is kept as written; by the protocol, H5 is refuted.
- **Lines of code.** The types of the summary are declared in `summary.ts` for A and B, which is not counted; C declares them in its own file, as `export struct`. They are left out of C's count alike.
- **A collection before each timed run**, `gc()` with `--expose-gc`, so that a version does not pay for the garbage of the one before.
- **Memory.** The largest `VmHWM` among the renderer processes of a browser launched for the run, the page being the only one open.
- **The throttled network**, exploratory: 9 Mb/s down, 1.5 up, 170 ms of latency, at 100,000 rows only, 3 loads: at that speed, 140 MB would take two minutes a load.
- **Two bugs of the compiler** were found by writing C, both refused by its release verifier rather than shipped, and fixed with a test each before the measure (commit `e1f58b4`; [findings](../findings.md), F001 and F002).

### Run 1, at commit `b06da25`: the results

Measured on 2026-11-11 from 06:54 to 07:02 UTC, on an Intel Xeon at 2.10 GHz with 4 cores, Chromium headless; the whole report is in [bench/data/RESULTS.md](../../../bench/data/RESULTS.md) and every number in its `results.json`. The three versions give the same summary, byte for byte, at every size.

| Hypothesis                                          | Verdict     | Measured                                                       |
| --------------------------------------------------- | ----------- | -------------------------------------------------------------- |
| H1, plain Peras beats plain TypeScript              | **refuted** | C at 0.85 times A's speed at 1,000,000 rows, 0.88 at 4,000,000 |
| H2, plain Peras comes close to optimized TypeScript | **refuted** | C at 0.10 times B's speed at 1,000,000 rows, 0.09 at 4,000,000 |
| H3, less memory                                     | **refuted** | C's peak 1.12 times A's at 4,000,000 rows                      |
| H4, a small program                                 | **refuted** | C ships 12,169 bytes, 15.4 times A's 788                       |
| H5, the cores help                                  | **refuted** | D cannot be written (E0241)                                    |
| H6, linear                                          | holds       | C's time at 4,000,000 rows is 4.17 times its time at 1,000,000 |
| H7, no more code                                    | holds       | C counts 99 lines, 1.08 times A's 92                           |

Warm, in milliseconds, medians of 15 runs:

| Version                  | 100,000 | 1,000,000 | 4,000,000 |
| ------------------------ | ------: | --------: | --------: |
| A. TypeScript, idiomatic |    75.7 |   1,015.4 |   4,360.4 |
| B. TypeScript, optimized |    12.8 |     121.5 |     469.1 |
| C. Peras                 |   105.6 |   1,193.0 |   4,976.5 |

The runs do not overlap where it matters: at 4,000,000 rows, C's fifteen times lie between 4,776 and 5,507 ms, all above A's median. Cold, the first chart comes in the same order, 5.5 s for C, 4.8 for A and 0.9 for B at 4,000,000 rows; under the throttled network, at 100,000 rows, the download takes nearly all of it, 3.7 to 3.8 s for every version.

### Analysis

- **Where C loses its time.** A profile made while writing C, at 1,000,000 rows in Node, outside the protocol: handing the text to the module costs 7 ms, splitting it into lines 20 ms, into fields 126 ms, against 586 ms for JavaScript's `split`; reading two integers per row with `parseI32` brings it to 434 ms, about 150 ns per integer, and the maps keyed by strings built per row to 793 ms. Peras splits text faster than JavaScript; it loses on reading integers and on maps keyed by strings ([findings](../findings.md) F201, F202).
- **The headroom is there.** B shows what the machine allows for the same work: 8.4 to 9.3 times A's speed, and 9.8 to 10.6 times C's, at 1,000,000 and 4,000,000 rows. Nothing in the data or the query prevents a compiled language from reaching it; what prevents Peras is its runtime's integer parsing, its string-keyed maps, and the copy of the text into the module.
- **Memory.** C holds the text a second time, copied into its linear memory, which WebAssembly does not give back; at 4,000,000 rows that copy alone is 122 MiB. That is why C's peak exceeds A's, where the text is shared with the decoded string.
- **The program.** C ships its runtime, the maps, the strings, the sort: 12,169 bytes, against 788 for A, which uses JavaScript's own. At 100,000 rows under a throttled network, the difference is lost in the download of the data, 3.7 to 3.8 s for every version.
- **What holds.** C's cost grows linearly with the rows, and it is written in as many lines as the TypeScript, 99 against 92, with the same structure: plain Peras is no harder to write for this job, it is slower.

### What it means

On ingesting text data, the claim this study tested, Peras does not deliver today: plain Peras is slower than plain TypeScript, holds more memory and ships fifteen times more code, and cannot use the cores. The study says so, and says why, in terms the compiler can act on. In the order the measures give, as decision 0011 orders its steps:

1. **Read integers fast**: `parseI32` at the speed of a loop over bytes (F201).
2. **Maps keyed by strings without a string per row**: a key looked up from the slice it comes from, copied only when new (F202).
3. **No copy of the text**: read the bytes where they are, which needs `u8` compiled (F302), the next step already decided.
4. **Aggregate on the cores**: `parallel for` with a reduction per thread and allocation in a turn (F301).
5. **A lighter runtime** for what a module does not use (F203).

Each will be measured again under this protocol, unchanged, as a run 2 and further, and reported whatever it gives.

### Limits

- **Memory below the loading peak is not seen.** `VmHWM` rises only past its highest point; loading the file, as the response and its array buffer, already reaches a peak. B's query stays below it at 1,000,000 and 4,000,000 rows, and its memory reads 0: not nothing, but less than loading the data. A and C both go past it, which keeps H3 readable.
- The other limits are those registered: generated data without quotes, versions written by the authors, one machine.
