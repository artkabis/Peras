# 0038: JSON

_French translation: [../../fr/decisions/0038-json.md](../../fr/decisions/0038-json.md)._

_Status: protocol registered on 2026-11-18, before any prototype and any measure, as the rule of the project asks; managed options measured at `0f1cdd6`, the owned ways not built; proposal: j1. It starts the "data" line of phase 3 of the [roadmap](../reference/roadmap.md), whose example reads `Settings.fromJson(await response.text())?`. Under the owner's rule of 2026-11-17, the option chosen must be an improvement, never a regression._

## Context

What Peras does today, read before writing this (finding M020):

- **No JSON in the language.** No method, type or runtime function reads or writes it, in either mode.
- **A managed module reads it through an `extern` block** ([decision 0010](0010-calling-javascript.md)): a JavaScript file of the user's calls `JSON.parse`, and the value it gives is checked against the declared type at the boundary. An `extern` function is not generic: one function per type read, and a value of the wrong shape throws a `TypeError`, not a value the program can test.
- **An owned module takes structures from JavaScript** ([decision 0021](0021-phases-4-and-5.md)): the loader copies an object into a structure by the shape of each parameter (`Shape` in `crates/perasc-ir/src/lib.rs`). A TypeScript application can parse JSON and pass the object to an exported function; Peras code cannot parse a text it holds.

## Options

- **j0. As today**: `extern` and `JSON.parse` in a managed module; in an owned one, the application parses and passes the object.
- **j1. Typed JSON, derived by the compiler**: `T.fromJson(text): Result<T, JsonError>` and `x.toJson(): String`, for every `T` made of numbers, booleans, strings, arrays, options, maps keyed by strings, structures and enumerations. `JsonError` says where and what: the path (`items[3].price`), what was expected, what was found. Two ways in an owned module, measured apart:
  - **j1h**, through the host: the text goes to JavaScript's `JSON.parse`, then the loader copies the value in by its shape, as it copies a parameter;
  - **j1w**, in WebAssembly: a parser in the module fills the value from the text's bytes, never through JavaScript.
    A managed module has one way, `JSON.parse`, then the value checked against `T`.
- **j2. A JSON value**: `Json`, an enumeration (`Null`, `Bool`, `Number`, `Text`, `List`, `Object`), `Json.parse(text): Result<Json, JsonError>`, `json.toText()`, and reading by `get("key")`, `at(i)`, `asNumber()`… each giving an option.

## Protocol, registered before any prototype

Each option is prototyped behind `PERAS_PROTO_JSON`; the build without it keeps today's behaviour, j0. Every module measured is a production build, named (`--allocator tlsf`, finding M029).

1. **Ease of writing**, four programs written for each option, in a managed and in an owned module where the option allows it, counted as decision 0028 counts them (lines, notions to learn, errors met while writing):
   - **P1**, settings read from a text into a structure: a nested structure, an array of structures, an optional field, an enumeration; an invalid text answered with a message that names the field;
   - **P2**, 100,000 records read from a text, one field summed;
   - **P3**, a summary written as JSON, as decision 0014 writes its summary;
   - **P4**, five invalid texts (malformed, a missing field, a wrong type, a number out of range for its integer, an unknown variant): what each option tells the program, and whether a wrong value can pass unseen.
2. **Correctness**: each program gives TypeScript's result; `toJson` then `fromJson` gives the value back; P4's texts are refused, never read as a wrong value; an end-to-end test in both modes.
3. **Speed and load on the processor**, in Node, TypeScript (`JSON.parse`, then the fields checked by hand as a careful program does, no npm package) and every option's module in one process, the order alternating, 21 rounds, the median of the ratios round by round and their range (finding M017), the CPU time over the wall time:
   - **W1**, a text of 100,000 records, about 10 MB, read and one field summed (P2);
   - **W2**, 100,000 records written as JSON;
   - **W3**, a small text read 100,000 times (P1's settings), where the cost of crossing to JavaScript counts most.
4. **Bytes**: each module, raw and gzipped, and every module of the repository by `scripts/check-regression.mjs` under each option, which also gives the compile time and the compiler's size.
5. **An option not built** is reported as such, with why, never ranked by a guess (finding M001).

`node scripts/bench-json.mjs` runs points 3 and 4's workloads; `--check` checks every option's results against TypeScript's, and is run with every check of the project.

## Record

_Each part is recorded here as it lands._

### Precisions of the protocol (2026-11-18), before any measure

Fixed by the first prototype, before anything is measured:

- **`JsonError` is a `String` in the prototypes**: `path: expected what, found what`, the path from the value read (`servers[0].port`), a malformed text named `the text`. A structure of its own would change no measure; it is left to the decision.
- **An enumeration is written as JSON writes one**: a variant without data as its name, `"Dark"`; a variant with data as an object of one key, `{ "Circle": [2.5] }`. P1's text writes its theme `"Dark"` for every option; j0's conversion by hand reads that.
- **A 64-bit integer** is read from a JSON number only when it is exact in a float, `Number.isSafeInteger`; written, it is a number.
- **`T.fromJson` exists for a structure or an enumeration** of the program: P2 reads its records as a structure holding the array, which j1 asks of a program and is counted with its ease.
- **j1 in a managed module is the first prototype**; in an owned module, `fromJson` is refused with E0900 until j1h or j1w is built.

### The measure (2026-11-18)

Two runs at commit 0f1cdd6, one after the other, nothing else running, every module a managed module built for production; every table in [`bench/json/RESULTS.md`](../../../bench/json/RESULTS.md), with the machine (an Intel Xeon at 2.10 GHz). The owned ways, j1h and j1w, and j2 in an owned module, are **not built**: j1h needs a call from the module to its host that gives a structure back, which the loader cannot do, copying only an export's parameters in and its results out; j1w needs a JSON parser in the WebAssembly runtime; each is days of work, which the owner chose to leave to a later decision once this one has chosen the shape of the API (2026-11-18). They are not ranked (finding M001).

Ease, lines of code (blank lines and comments left out), and errors met while writing (`bench/json/ease/LOG.md`):

| Option | P1, settings | P2, records summed | P3, a summary | W2, records written | JavaScript needed | Errors met |
| ------ | -----------: | -----------------: | ------------: | ------------------: | ----------------: | ---------- |
| j0     |           49 |                 19 |            18 |                  16 |                 4 | 1          |
| j1     |           25 |                 23 |            15 |                  13 |                 0 | 0          |
| j2     |           82 |                 22 |            15 |                  12 |                 0 | 1          |

P4, the five invalid texts: no option reads one as a wrong value. j0 throws four of them as exceptions the program cannot test, their messages not naming the field; j1 gives five errors it tests, each naming the field and what was found; j2 gives five too, with the messages the program wrote itself, field by field.

Speed, ratios to the reference written by hand (`JSON.parse`, then each field checked), median of 21 rounds, run 1 then run 2:

| Workload                                 | j0, today     | j1            | j2          |
| ---------------------------------------- | ------------- | ------------- | ----------- |
| W1, 100,000 records read, a field summed | 1.40, 1.28    | 3.09, 3.12    | 3.56, 3.48  |
| W2, 100,000 records written              | 1.03, 1.02    | 1.99, 2.16    | 3.62, 3.79  |
| W3, the settings read 100,000 times      | 1.49, 1.54    | 2.45, 2.46    | 2.79, 2.70  |
| Bytes of W1's module (gzip)              | 3,816 (1,398) | 6,105 (1,859) | 2,756 (843) |

- **j0 is the fastest**: it checks the value `JSON.parse` gives with `$shape`, whose checkers are made once; it is also the one whose errors a program cannot handle.
- **j1 takes twice to three times the reference's time**: its reader walks the shape at each value and builds the path of each value as it goes, `items[3].price`, whether or not something is wrong. That this is its cost is a possible cause, not a measured one (finding M001); a reader made once per type, its path built only for an error, is what a landing would measure.
- **j2 is the slowest on every workload**, 2.7 to 3.8 times the reference: every value of the text is wrapped as a `Json` object, then read through methods that give options.
- **The CPU time over the wall time** is 1.5 to 2.0 for j1 and j2, against 1.1 to 1.3 for j0 and the reference: the engine's collector, on other threads, works for the objects they make.
- **Non-regression**, `scripts/check-regression.mjs 6c10ddf` under j1 and under j2: 177 modules compared, none changed; only this decision's programs build now, which nothing built before; compile time 0.98 to 1.01. A first run of it exported `PERAS_PROTO_JSON` to both compilers, the reference included, which has the prototypes: it compared each option with itself, and was run again with the option given to today's compiler only.

### Proposal

**j1**, `T.fromJson(text)` and `x.toJson()`: the shortest programs where the shape is known, P1 in 25 lines against 49 and 82, no JavaScript to write, every invalid text an error the program tests that names the field, and faster than j2 on every workload. Its cost is speed against today's `extern`: a landing makes its reader once per type and builds a path only for an error, and is measured against j0 before it lands. j2 is the way to read a JSON whose shape is not known; the programs here all know theirs, so it is measured, not proposed. The owner decides.
