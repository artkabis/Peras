# 0038 : JSON

_Version anglaise : [../../en/decisions/0038-json.md](../../en/decisions/0038-json.md)._

_État : protocole enregistré le 2026-11-18, avant tout prototype et toute mesure, comme le demande la règle du projet. Il ouvre la ligne « données » de la phase 3 de la [feuille de route](../reference/roadmap.md), dont l’exemple lit `Settings.fromJson(await response.text())?`. Sous la règle du propriétaire du 2026-11-17, l’option retenue doit être une amélioration, jamais une régression._

## Contexte

Ce que fait Peras aujourd’hui, lu avant d’écrire ceci (constat M020) :

- **Pas de JSON dans le langage.** Aucune méthode, aucun type ni aucune fonction du runtime ne le lit ou ne l’écrit, dans aucun mode.
- **Un module managed le lit par un bloc `extern`** ([décision 0010](0010-calling-javascript.md)) : un fichier JavaScript de l’utilisateur appelle `JSON.parse`, et la valeur qu’il donne est vérifiée contre le type déclaré à la frontière. Une fonction `extern` n’est pas générique : une fonction par type lu, et une valeur de mauvaise forme lève une `TypeError`, pas une valeur que le programme peut tester.
- **Un module owned reçoit des structures de JavaScript** ([décision 0021](0021-phases-4-and-5.md)) : le chargeur copie un objet dans une structure selon la forme de chaque paramètre (`Shape` dans `crates/perasc-ir/src/lib.rs`). Une application TypeScript peut analyser du JSON et passer l’objet à une fonction exportée ; le code Peras ne peut pas analyser un texte qu’il tient.

## Options

- **j0. Comme aujourd’hui** : `extern` et `JSON.parse` dans un module managed ; dans un module owned, l’application analyse et passe l’objet.
- **j1. Du JSON typé, dérivé par le compilateur** : `T.fromJson(text): Result<T, JsonError>` et `x.toJson(): String`, pour chaque `T` fait de nombres, de booléens, de chaînes, de tableaux, d’options, de tables à clés textuelles, de structures et d’énumérations. `JsonError` dit où et quoi : le chemin (`items[3].price`), ce qui était attendu, ce qui a été trouvé. Deux façons dans un module owned, mesurées à part :
  - **j1h**, par l’hôte : le texte va au `JSON.parse` de JavaScript, puis le chargeur copie la valeur selon sa forme, comme il copie un paramètre ;
  - **j1w**, en WebAssembly : un analyseur dans le module remplit la valeur à partir des octets du texte, sans jamais passer par JavaScript.
    Un module managed a une seule façon, `JSON.parse`, puis la valeur vérifiée contre `T`.
- **j2. Une valeur JSON** : `Json`, une énumération (`Null`, `Bool`, `Number`, `Text`, `List`, `Object`), `Json.parse(text): Result<Json, JsonError>`, `json.toText()`, et la lecture par `get("key")`, `at(i)`, `asNumber()`… chacune donnant une option.

## Protocole, enregistré avant tout prototype

Chaque option est prototypée derrière `PERAS_PROTO_JSON` ; le build sans elle garde le comportement d’aujourd’hui, j0. Chaque module mesuré est un build de production, nommé (`--allocator tlsf`, constat M029).

1. **Facilité d’écriture**, quatre programmes écrits pour chaque option, dans un module managed et dans un module owned là où l’option le permet, comptés comme la décision 0028 les compte (lignes, notions à apprendre, erreurs rencontrées en écrivant) :
   - **P1**, des réglages lus d’un texte dans une structure : une structure imbriquée, un tableau de structures, un champ optionnel, une énumération ; un texte invalide répondu par un message qui nomme le champ ;
   - **P2**, 100 000 enregistrements lus d’un texte, un champ sommé ;
   - **P3**, un résumé écrit en JSON, comme la décision 0014 écrit son résumé ;
   - **P4**, cinq textes invalides (mal formé, un champ manquant, un mauvais type, un nombre hors de l’intervalle de son entier, une variante inconnue) : ce que chaque option dit au programme, et si une mauvaise valeur peut passer inaperçue.
2. **Justesse** : chaque programme donne le résultat du TypeScript ; `toJson` puis `fromJson` rend la valeur ; les textes de P4 sont refusés, jamais lus comme une mauvaise valeur ; un test de bout en bout dans les deux modes.
3. **Vitesse et charge du processeur**, dans Node, le TypeScript (`JSON.parse`, puis les champs vérifiés à la main comme le fait un programme soigneux, sans paquet npm) et le module de chaque option dans un même processus, l’ordre alternant, 21 tours, la médiane des rapports tour par tour et leur étendue (constat M017), le temps CPU sur le temps réel :
   - **W1**, un texte de 100 000 enregistrements, environ 10 Mo, lu et un champ sommé (P2) ;
   - **W2**, 100 000 enregistrements écrits en JSON ;
   - **W3**, un petit texte lu 100 000 fois (les réglages de P1), là où le coût du passage par JavaScript compte le plus.
4. **Octets** : chaque module, brut et en gzip, et chaque module du dépôt par `scripts/check-regression.mjs` sous chaque option, qui donne aussi le temps de compilation et la taille du compilateur.
5. **Une option non construite** est dite telle, avec pourquoi, jamais classée sur une supposition (constat M001).

`node scripts/bench-json.mjs` lance les charges des points 3 et 4 ; `--check` vérifie les résultats de chaque option contre ceux du TypeScript, et tourne avec chaque vérification du projet.
