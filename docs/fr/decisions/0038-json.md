# 0038 : JSON

_Version anglaise : [../../en/decisions/0038-json.md](../../en/decisions/0038-json.md)._

_État : protocole enregistré le 2026-11-18, avant tout prototype et toute mesure, comme le demande la règle du projet ; options managed mesurées au commit `0f1cdd6`, les voies owned non construites ; proposition : j1. Il ouvre la ligne « données » de la phase 3 de la [feuille de route](../reference/roadmap.md), dont l’exemple lit `Settings.fromJson(await response.text())?`. Sous la règle du propriétaire du 2026-11-17, l’option retenue doit être une amélioration, jamais une régression._

## Contexte

Ce que fait Peras aujourd’hui, lu avant d’écrire ceci (constat M020) :

- **Pas de JSON dans le langage.** Aucune méthode, aucun type ni aucune fonction du runtime ne le lit ou ne l’écrit, dans aucun mode.
- **Un module managed le lit par un bloc `extern`** ([décision 0010](0010-calling-javascript.md)) : un fichier JavaScript de l’utilisateur appelle `JSON.parse`, et la valeur qu’il donne est vérifiée contre le type déclaré à la frontière. Une fonction `extern` n’est pas générique : une fonction par type lu, et une valeur de mauvaise forme lève une `TypeError`, pas une valeur que le programme peut tester.
- **Un module owned reçoit des structures de JavaScript** ([décision 0021](0021-phases-4-and-5.md)) : le chargeur copie un objet dans une structure selon la forme de chaque paramètre (`Shape` dans `crates/perasc-ir/src/lib.rs`). Une application TypeScript peut analyser du JSON et passer l’objet à une fonction exportée ; le code Peras ne peut pas analyser un texte qu’il tient.

## Options

- **j0. Comme aujourd’hui** : `extern` et `JSON.parse` dans un module managed ; dans un module owned, l’application analyse et passe l’objet.
- **j1. Du JSON typé, dérivé par le compilateur** : `T.fromJson(text): Result<T, JsonError>` et `x.toJson(): String`, pour chaque `T` fait de nombres, de booléens, de chaînes, de tableaux, d’options, de tables à clés textuelles, de structures et d’énumérations. `JsonError` dit où et quoi : le chemin (`items[3].price`), ce qui était attendu, ce qui a été trouvé. Deux façons dans un module owned, mesurées à part :
  - **j1h**, par l’hôte : le texte va au `JSON.parse` de JavaScript, puis le chargeur copie la valeur selon sa forme, comme il copie un paramètre ;
  - **j1w**, en WebAssembly : un analyseur dans le module remplit la valeur à partir des octets du texte, sans jamais passer par JavaScript.
    Un module managed a une seule façon, `JSON.parse`, puis la valeur vérifiée contre `T`.
- **j2. Une valeur JSON** : `Json`, une énumération (`Null`, `Bool`, `Number`, `Text`, `List`, `Object`), `Json.parse(text): Result<Json, JsonError>`, `json.toText()`, et la lecture par `get("key")`, `at(i)`, `asNumber()`… chacune donnant une option.

## Protocole, enregistré avant tout prototype

Chaque option est prototypée derrière `PERAS_PROTO_JSON` ; le build sans elle garde le comportement d’aujourd’hui, j0. Chaque module mesuré est un build de production, nommé (`--allocator tlsf`, constat M029).

1. **Facilité d’écriture**, quatre programmes écrits pour chaque option, dans un module managed et dans un module owned là où l’option le permet, comptés comme la décision 0028 les compte (lignes, notions à apprendre, erreurs rencontrées en écrivant) :
   - **P1**, des réglages lus d’un texte dans une structure : une structure imbriquée, un tableau de structures, un champ optionnel, une énumération ; un texte invalide répondu par un message qui nomme le champ ;
   - **P2**, 100 000 enregistrements lus d’un texte, un champ sommé ;
   - **P3**, un résumé écrit en JSON, comme la décision 0014 écrit son résumé ;
   - **P4**, cinq textes invalides (mal formé, un champ manquant, un mauvais type, un nombre hors de l’intervalle de son entier, une variante inconnue) : ce que chaque option dit au programme, et si une mauvaise valeur peut passer inaperçue.
2. **Justesse** : chaque programme donne le résultat du TypeScript ; `toJson` puis `fromJson` rend la valeur ; les textes de P4 sont refusés, jamais lus comme une mauvaise valeur ; un test de bout en bout dans les deux modes.
3. **Vitesse et charge du processeur**, dans Node, le TypeScript (`JSON.parse`, puis les champs vérifiés à la main comme le fait un programme soigneux, sans paquet npm) et le module de chaque option dans un même processus, l’ordre alternant, 21 tours, la médiane des rapports tour par tour et leur étendue (constat M017), le temps CPU sur le temps réel :
   - **W1**, un texte de 100 000 enregistrements, environ 10 Mo, lu et un champ sommé (P2) ;
   - **W2**, 100 000 enregistrements écrits en JSON ;
   - **W3**, un petit texte lu 100 000 fois (les réglages de P1), là où le coût du passage par JavaScript compte le plus.
4. **Octets** : chaque module, brut et en gzip, et chaque module du dépôt par `scripts/check-regression.mjs` sous chaque option, qui donne aussi le temps de compilation et la taille du compilateur.
5. **Une option non construite** est dite telle, avec pourquoi, jamais classée sur une supposition (constat M001).

`node scripts/bench-json.mjs` lance les charges des points 3 et 4 ; `--check` vérifie les résultats de chaque option contre ceux du TypeScript, et tourne avec chaque vérification du projet.

## Registre

_Chaque partie est consignée ici à son arrivée._

### Précisions du protocole (2026-11-18), avant toute mesure

Fixées par le premier prototype, avant que rien ne soit mesuré :

- **`JsonError` est une `String` dans les prototypes** : `chemin: expected quoi, found quoi`, le chemin depuis la valeur lue (`servers[0].port`), un texte mal formé nommé `the text`. Une structure à elle ne changerait aucune mesure ; elle est laissée à la décision.
- **Une énumération s’écrit comme JSON en écrit une** : une variante sans données par son nom, `"Dark"` ; une variante avec données par un objet d’une clé, `{ "Circle": [2.5] }`. Le texte de P1 écrit son thème `"Dark"` pour chaque option ; la conversion à la main de j0 lit cela.
- **Un entier de 64 bits** n’est lu d’un nombre JSON que s’il est exact en flottant, `Number.isSafeInteger` ; écrit, c’est un nombre.
- **`T.fromJson` existe pour une structure ou une énumération** du programme : P2 lit ses enregistrements comme une structure qui tient le tableau, ce que j1 demande d’un programme et qui est compté avec sa facilité.
- **j1 dans un module managed est le premier prototype** ; dans un module owned, `fromJson` est refusé avec E0900 tant que j1h ou j1w n’est pas construit.

### La mesure (2026-11-18)

Deux exécutions au commit 0f1cdd6, l’une après l’autre, rien d’autre ne tournant, chaque module un module managed construit pour la production ; chaque tableau dans [`bench/json/RESULTS.md`](../../../bench/json/RESULTS.md), avec la machine (un Intel Xeon à 2,10 GHz). Les voies owned, j1h et j1w, et j2 dans un module owned, **ne sont pas construites** : j1h demande un appel du module vers son hôte qui rende une structure, ce que le chargeur ne sait pas faire, ne copiant que les paramètres d’un export à l’entrée et ses résultats à la sortie ; j1w demande un analyseur JSON dans le runtime WebAssembly ; chacune représente des jours de travail, que le propriétaire a choisi de laisser à une décision suivante une fois que celle-ci aura choisi la forme de l’API (2026-11-18). Elles ne sont pas classées (constat M001).

Facilité, lignes de code (lignes vides et commentaires exclus), et erreurs rencontrées en écrivant (`bench/json/ease/LOG.md`) :

P4, les cinq textes invalides : aucune option n’en lit un comme une mauvaise valeur. j0 en lève quatre comme des exceptions que le programme ne peut pas tester, leurs messages ne nommant pas le champ ; j1 donne cinq erreurs qu’il teste, chacune nommant le champ et ce qui a été trouvé ; j2 en donne cinq aussi, avec les messages que le programme a écrits lui-même, champ par champ.

Vitesse, rapports à la référence écrite à la main (`JSON.parse`, puis chaque champ vérifié), médiane de 21 tours, exécution 1 puis 2 :

| W1, 100 000 enregistrements lus, un champ sommé | 1,40, 1,28      | 3,09, 3,12    | 3,56, 3,48  |
| W2, 100 000 enregistrements écrits              | 1,03, 1,02      | 1,99, 2,16    | 3,62, 3,79  |
| W3, les réglages lus 100 000 fois               | 1,49, 1,54      | 2,45, 2,46    | 2,79, 2,70  |

- **j0 est le plus rapide** : il vérifie la valeur que donne `JSON.parse` avec `$shape`, dont les vérificateurs sont faits une fois ; c’est aussi celui dont un programme ne peut pas traiter les erreurs.
- **j1 prend deux à trois fois le temps de la référence** : son lecteur parcourt la forme à chaque valeur et construit le chemin de chaque valeur en avançant, `items[3].price`, qu’il y ait une faute ou non. Que ce soit son coût est une cause possible, non mesurée (constat M001) ; un lecteur fait une fois par type, son chemin construit seulement pour une erreur, est ce qu’une installation mesurerait.
- **j2 est le plus lent sur chaque charge**, 2,7 à 3,8 fois la référence : chaque valeur du texte est enveloppée dans un objet `Json`, puis lue par des méthodes qui donnent des options.
- **Le temps CPU sur le temps réel** est de 1,5 à 2,0 pour j1 et j2, contre 1,1 à 1,3 pour j0 et la référence : le ramasse-miettes du moteur, sur d’autres fils, travaille pour les objets qu’elles créent.
- **Non-régression**, `scripts/check-regression.mjs 6c10ddf` sous j1 et sous j2 : 177 modules comparés, aucun changé ; seuls les programmes de cette décision se construisent désormais, ce que rien ne construisait avant ; temps de compilation de 0,98 à 1,01. Une première exécution a exporté `PERAS_PROTO_JSON` vers les deux compilateurs, la référence comprise, qui a les prototypes : elle comparait chaque option à elle-même, et a été refaite avec l’option donnée au seul compilateur d’aujourd’hui.

### Proposition

**j1**, `T.fromJson(text)` et `x.toJson()` : les programmes les plus courts quand la forme est connue, P1 en 25 lignes contre 49 et 82, aucun JavaScript à écrire, chaque texte invalide une erreur que le programme teste et qui nomme le champ, et plus rapide que j2 sur chaque charge. Son coût est la vitesse face à l’`extern` d’aujourd’hui : une installation fait son lecteur une fois par type et ne construit un chemin que pour une erreur, et elle est mesurée face à j0 avant d’être installée. j2 est la façon de lire un JSON dont la forme n’est pas connue ; les programmes ici connaissent tous la leur, donc elle est mesurée, non proposée. Le propriétaire décide.

### Le lecteur de j1 fait une fois par type, mesuré face à j0 (2026-11-18)

Comme la proposition le demandait avant d’installer j1 (commit 8b81e2f) : `T.fromJson` garde un lecteur par type, fait la première fois à partir de sa forme, qui ne construit aucun chemin ; une valeur invalide est relue par le parcours qui nomme le chemin, si bien que chaque message est celui d’avant. `x.toJson()` écrit une valeur dont le type ne tient que des nombres, des chaînes, des booléens, des tableaux et des structures avec `JSON.stringify` seul. Exécutions 3 et 4, l’une après l’autre, rien d’autre ne tournant, dans [`bench/json/RESULTS.md`](../../../bench/json/RESULTS.md) :

| Charge                                          | j0, aujourd’hui | j1 avant   | j1, un lecteur par type | j2         |
| ----------------------------------------------- | --------------- | ---------- | ----------------------- | ---------- |
| W1, 100 000 enregistrements lus, un champ sommé | 1,68, 1,70      | 3,09, 3,12 | **1,54, 1,52**          | 3,48, 4,03 |
| W2, 100 000 enregistrements écrits              | 1,00, 1,08      | 1,99, 2,16 | **0,98, 1,01**          | 3,60, 3,46 |
| W3, les réglages lus 100 000 fois               | 1,53, 1,52      | 2,45, 2,46 | **1,45, 1,46**          | 2,77, 2,69 |

- **j1 est désormais aussi rapide que j0 ou plus sur chaque charge**, ses erreurs toujours des valeurs que le programme teste, nommant le champ.
- **Son coût est en octets** : le module de W1 livre 2 305 octets en gzip, contre 1 619 pour j0 compté de la même façon (constat M006), ses 1 398 et les 221 du `json.js` qu’il demande ; 686 octets de plus, les lecteurs du runtime, les mêmes quel que soit le programme. Aucun module du dépôt ne change.
- Les rapports de j0 diffèrent des exécutions 1 et 2 (1,68 contre 1,28 à 1,40 sur W1) : une autre machine, la même session (constat M016) ; seuls les rapports d’une même exécution se comparent.

### Proposition, après la mesure face à j0

**j1** : aussi rapide que l’`extern` d’aujourd’hui ou plus sur chaque charge, des programmes deux fois plus courts, chaque texte invalide une erreur que le programme teste et qui nomme le champ, pour 686 octets de plus en gzip dans un module qui lit du JSON. Le propriétaire décide.
